# 交付脚本的格式检查与适配修复

每个交付脚本在写入绑定之前都要过一遍格式检查，用的是 datacom-fault-tree-tester 同一份 `check_contract.py`（本技能 `engine/` 里有副本，单独安装也能用）。本文说明检查结果分几档、每档怎么处理、哪些修改允许、哪些不允许。正文 SKILL.md 只给命令，脚本报出检查结果时读本文。

## 1. 原则：不修改判断逻辑

交付脚本是业务同事写的、用样本数据验证过的。本技能只负责把它接进场景技能，不负责改它的判断。发现脚本可疑（比如解析失败还继续给判断），告诉用户反馈给交付方，不代为修改。

允许改的只有输入输出格式的适配问题：入口函数名、数据文件后缀、返回值形态这一类；并且只改本技能保存的副本，不改交付包里的原件。

## 2. 检查结果的两档

执行时脚本由通用适配函数 `fault_check` 调用。适配函数能弥补的问题放行，不能弥补的问题拦下：

- **WARN，适配函数能弥补 → 放行，脚本不动。** 入口用了旧名字、只按单个网元写、返回布尔值而不是三态、按网元返回字典、用 `print` 而不是返回值、读了 `argv` 这类。运行时由适配函数统一处理（仲裁多网元结果、保护现场、归一返回形态）。迁移记录写 `contract_warns`，并列入退回交付方的清单。
- **FAIL，适配函数弥补不了、执行必受影响 → 不写绑定，进入修复。** 例如只识别 `.txt` 而漏掉 `log.log`、缺数据时返回"不成立"而不是"数据不足"、import 了第三方库。处理方法：
  1. 脚本副本和修复基准先放到产物 `scripts/custom/`（`<脚本>` 和 `<脚本>.orig`）。
  2. 按检查输出给出的修法，只改副本里的输入输出适配部分。判断不了某处改动是否属于判断逻辑时，先问用户，不自行判断。
  3. 改完重跑同一条迁移命令继续。包没变时修复过的副本不会被包里的原件覆盖；检查通过后绑定才写入。

## 3. 配套机制

- **补齐共享模块**：脚本 import 的 `search_*.py` 包里没带时，从同一 skills 目录下的 datacom-fault-tree-tester 或本技能 `engine/` 复制一份进 `scripts/custom/`。这是违规项，记入退回清单：交付包本应自包含（tester 规范附录 8）。
- **回归检查**：包里带 `测试数据/` 时，检查阶段会自动用它试跑一次并记下结果基线；修复副本之后再跑一次，`matched` 与修前不一致就拦下，适配修复不许改变判断结论。
- **退回交付方的清单**：汇总末尾按包列出"适配函数弥补了哪些 WARN、修了哪些适配问题、补了哪些库"。副本上的修复只对本次执行有效，原件的问题必须回到交付方手里（或用 tester 的"批量翻新存量交付包"功能更新原件），否则每次全量交付都会再出现一遍。
- **留痕**：迁移记录字段 `contract_warns`、`repairs`；`scripts/custom/` 下的 `.orig`（修复基准）和 `<脚本名去后缀>.contract.json`（检查记录）。想丢弃修复、按包里原件重来：删掉对应的 `.orig`，加 `--force` 重迁。

## 4. 入口函数

脚本的入口函数自动探测（`diagnose`、`main`、`check_ne` 等常见名字）。探测不准时脚本会报错或告警，按提示加 `--entry <函数名>`、`--per-ne`（入口只接收单个网元目录）、`--entry-kwargs '<JSON>'`（额外参数）重跑。探测不到就问用户或打开脚本看，不自行猜测函数名。
