# cs-scot-migrate：把节点交付包迁移进场景技能

## 任务

业务同事用 datacom-fault-tree-tester 产出节点交付包，里面是人确认过的判断方法文档和用样本数据验证过的判断脚本。本技能把它装进场景技能，做两件事：

1. **判据替换**：把判断方法文档全文逐字替换到故障树对应节点的判据上（故障描述、判断条件、命中条件、输出、数据来源表、注意事项一项不丢，写进调优表的 `判据:原文` 列）。树上的判据从此就是整份规范文档，数据来源表留作核对采集覆盖的依据。
2. **绑定替换**：清掉该节点原有的全部绑定，换成一条 S 类绑定。执行时由通用适配函数 `fault_check` 直接调用交付的脚本，脚本一行不改，判断逻辑原样接收，对错归脚本。

全部修改都通过产物自带的调优表往返完成（导出 → 改行 → 导入），复用它的全部校验；迁移记录写在 `产物/tree/migrations.json`。

## 术语

| 术语 | 含义 |
|---|---|
| 节点交付包 | tester 产出的 `<节点名>.zip` 或解压后的目录：`判断方法_<节点名>.md`、`fault_check_<节点名>.py`、`测试数据/` |
| 合集包 | 一个 zip 或目录里装着多个节点交付包 |
| 场景技能、产物 | generate 生成的技能目录；产物是它的 `assets/` 目录，含 `tree/`、`scripts/`、`plan.json` |
| 判据 | 故障树节点上的判断条件原文 |
| 绑定 | 节点判据与执行方式的对应；S 类绑定指"运行交付的判断脚本" |
| 对应表 | 每行一个节点的 xlsx 或 csv，写明节点路径、对应的 zip、判据、解决方案、是否要改；平台每次优化给的全量表就是它 |
| 调优表 | 产物自带的 `tree/<短名>.tuning.xlsx`，一行一个节点，是树和绑定的可编辑事实源 |
| 迁移记录 | `tree/migrations.json`，记每个节点迁自哪个包、内容指纹、时间、检查结果 |
| 工具链公共文件 | 与场景无关、由工具链维护的文件：引擎脚本、runner、check_data、zip2csv、fault-tree-rca 规则副本、执行指引正文 |
| 同一 skills 目录下的其他技能 | 与本技能并列安装的 cs-scot-generate、cs-scot-execute、fault-tree-rca、zip2csv、datacom-fault-tree-tester；发行包形态下它们在包根 |
| `engine/` | 本技能自带的公共文件副本，单独安装、旁边没有其他技能时用它 |
| 格式检查 | 用 tester 的 `check_contract.py` 检查交付脚本是否符合约定的输入输出格式 |

## 输入

| 参数 | 说明 |
|---|---|
| 交付包 | 单个节点交付包，或合集包；配合 `--auto` 批量处理 |
| 产物目录 | 场景技能的 `assets/` 目录，或独立的产物目录；给技能根目录也可以，脚本会自动定位到 `assets/` |
| 对应表（可选） | `--map <表路径>`；表放在交付包里会自动发现 |

## 执行规矩

- 不做脚本没要求的预先检查。节点对不对得上、包里有什么、树上有没有同名节点，都是第一步命令自己的输出，直接跑命令，按退出码处理。预先检查曾经花掉十几分钟，而命令本身几十秒就跑完。
- 不要用 `python -c` 或临时脚本解析 tree_index、调优表、产物 JSON：Windows 上中文路径经 shell 传递会乱码，字段结构靠猜必错。要看内容用本技能脚本的打印；还不够就把文件路径报给用户。
- 脚本报错时把报错原文给用户。产物不会写一半：所有修改在导入校验全部通过后才生效。
- 不改交付脚本的判断逻辑。允许改的只有输入输出格式的适配问题，而且只改副本，见 `references/script_check.md`。

## 执行步骤

### 第 1 步：确认输入

确认三样：交付包（单包、合集目录或 zip）的路径；产物目录（场景技能的 `assets/` 或技能根目录）；有没有对应表（`--map <表>`，或表已放在交付包里）。缺产物目录就问用户，不在文件系统里找。

### 第 2 步：运行迁移命令

```bash
python skills/cs-scot-migrate/scripts/migrate_fault_check.py \
    --package <交付包（单包、合集目录或 zip）> --product <产物或技能目录> --auto [--map <表>]
```

脚本按输入自动选择处理方式：

| 输入 | 处理方式 |
|---|---|
| 包里有对应表，或给了 `--map` | 按表批量：路径定位节点，按 zip 列匹配包（见"按对应表批量"） |
| 没有表，合集包 | 逐个子包按节点名精确匹配；没匹配上的列出候选 |
| 没有表，单个节点包 | 单节点流程：精确匹配就直接迁移 |
| 带 `--node`、`--only` 等手工参数 | 按手工指定执行，不再自动发现 |

脚本自己会依次做：预导入调优表（有未导入的人工修改时）、刷新工具链公共文件、格式检查交付脚本、修改调优表并导入、升级 `cross_analyzer.py` 的框架代码、写迁移记录。细节见"脚本自动做的事"。

### 第 3 步：看退出码

- 退出码 0：全部迁移成功，进入第 6 步汇报。
- 退出码 3：有节点没匹配上，脚本已打印候选列表（按相似度排序）和补充匹配的命令，进入第 4 步。
- 其他非 0 退出码：脚本报错，把报错原文给用户；常见的是调优表填坏了导入失败，或格式检查不通过（处理方法见 `references/script_check.md`）。

节点匹配分三级：第一级由代码精确匹配（交付包的节点名与树上某个节点一字不差且唯一），第二级由模型按语义匹配（第 4 步），第三级问用户（第 5 步）。

### 第 4 步：按语义补充匹配

看候选列表和交付包的判断方法文档，判断哪个节点与交付包说的是同一个故障。名字变体很常见，如"V-STP根桥桥MAC配置异常"与"V-STP根桥未配置桥MAC"。确信是同一个节点时，用候选列表附的命令执行迁移，并在汇报里写明"按语义把「<包节点名>」对应到 <节点号>「<树节点名>」"：

```bash
# 单个交付包
python skills/cs-scot-migrate/scripts/migrate_fault_check.py \
    --package <交付包> --product <产物目录> --node <节点号>
# 合集包里的某个子包
python skills/cs-scot-migrate/scripts/migrate_fault_check.py \
    --package <合集包> --product <产物目录> --only "<包节点名>" --node <节点号>
```

`--only` 从合集包里选定一个子包；单节点的参数 `--entry`、`--per-ne`、`--entry-kwargs` 都可以配。

### 第 5 步：拿不准就问用户

候选分数接近，或都不像同一个故障，把候选列表给用户，让用户指定节点号后再执行。不要在拿不准时选分数最高的。

### 第 6 步：汇报

原样列出脚本打印的汇总行和失败清单；按语义匹配的写明对应关系；退回交付方的清单单独列出；工具链公共文件的刷新清单原样列出，不自己总结成"已刷新某某"。

## 按对应表批量

对应表每行一个节点：层级列拼出路径定位节点（同名节点靠完整路径区分），zip 列匹配包。表头的写法宽松，平台的全量表可以直接使用。三种模式对应平台优化按钮的 optimizeType：

```bash
python skills/cs-scot-migrate/scripts/migrate_fault_check.py \
    --package <包目录> --product <产物> --auto --map <表> [--map-mode multi|all]
```

- 缺省 `auto`：迁移、更新判据、清除判据、同步解决方案都做；带 zip 的新行新增节点；表里没出现的节点只列出不删。
- `multi`（部分表）：不动树结构，不新增节点。
- `all`（全量表）：树结构以表为准，表里没出现的节点删除（三道防误删检查），只有判据的新行也建结构节点。

表带 `Need_Optimize` 列时，内容动作只对 TRUE 行执行，FALSE 行只用来对照结构。全部 FALSE 且表与树一致，等于只刷新技能。表头识别、每一行的处理规则、清除判据的规则、三种模式的完整对照和防误删检查，见 `references/mapping_table.md`；收表前先读它。

## 脚本自动做的事

每次迁移，脚本按顺序做：

1. 调优表比 tree_index 新（可能有未导入的人工修改）时先导入，再按新树匹配。表填坏了导入会失败，迁移停在这里，把报错原样给用户。
2. **刷新工具链公共文件**：逐文件与同一 skills 目录下的其他技能比对，内容不同就刷新，旧文件留 `.bak`；旁边没有其他技能时用 `engine/` 里的副本。规则见"无包刷新"一节。
3. **格式检查**：每个交付脚本过一遍 `check_contract.py`，按适配函数能否弥补分两档处理，见 `references/script_check.md`；脚本 import 的共享模块包里没带时补齐一份。
4. 把脚本复制进产物 `scripts/custom/`，修改调优表（判据与绑定），导入编译回产物，回导调优表保持同步。
5. 产物里 `cross_analyzer.py` 的框架代码过旧时就地升级（绑定内容不动）。
6. 写迁移记录。

入口函数自动探测（`diagnose`、`main`、`check_ne` 等）；探测不准时按提示加 `--entry <函数名>`、`--per-ne`、`--entry-kwargs '<JSON>'` 重跑。探测不到就问用户或打开脚本看，不自行猜测。

## 无包刷新：`--refresh-only`

手头没有交付包，只想把旧产物或旧场景技能刷到当前版本：

```bash
python skills/cs-scot-migrate/scripts/migrate_fault_check.py --product <产物或技能目录> --refresh-only
```

规则：工具链公共文件逐个与同一 skills 目录下的其他技能比对（行尾差异不算），内容不同就刷新，旧文件留 `.bak`；场景相关的文件一概不碰。

| 会刷新（工具链公共文件） | 不碰（场景相关） |
|---|---|
| `assets/scripts/` 下的引擎脚本：condition_kernels、xlsx_reader、custom_lib（没有手工注册函数时）、import_tree_excel、export_tree_excel | `assets/tree/`、`assets/plan.json`、knowledge.md |
| 技能根目录的 `scripts/runner.py`、`check_data.py`、`tree_prune.py` 和 `references/` | `assets/scripts/*_analyzer.py`（各指标脚本） |
| `assets/zip2csv/` 逐文件 | `assets/scripts/cross_analyzer.py`（只升级框架，绑定不动） |
| `assets/fault-tree-rca/`（有文件不同就整目录刷新，旧副本备份为 `fault-tree-rca.bak`） | `assets/scripts/custom/`（节点脚本与随包共享模块） |
| `SKILL.md` 正文（换正文，保留技能名和描述，旧文备份为 `SKILL.md.bak`） | custom_lib.py 里手工注册的函数 |

来源文件先通过能力标记核验，不合格的来源不用。以本机安装的工具链为准，所以装技能的机器要保持工具链最新。

脚本结束时逐项打印本次动了哪些文件，或者明确说"没有文件需要刷新"。汇报只许原样列出这份清单，不要自己总结成"已刷新某某"。

## 迁移后

- 执行诊断时可加 `--data raw=<zip2csv 输出的 extracted 目录>`，让脚本直接读原始日志文件，最忠实；不加也能跑，适配函数会从 config、log、cmd 三张表重建输入。
- 判断结果三态：任一网元命中 → 成立；全部网元报错或没有网元 → 数据不足（不当作"正常"）；其余 → 不成立。
- 证据保真：脚本给出的命中原文（`matched_items`）、出处文件（`source_files`）、判定理由（`details.reason`）逐字进事实（定长截断，防止上下文过长），随 rca_input 带进根因报告。
- 产物就是场景技能的 `assets/` 时，迁移就地生效，技能已更新完毕，不用重新打包；只有在独立产物目录上迁移、之后要发布成技能时才跑 `package_scenario.py`。
- 同一节点重复迁移（交付包更新）就重跑同一条命令，迁移记录覆盖更新。

## 完整例子

场景技能 `D:\技能\access-failure-demo\`，同事给了合集包 `D:\交付\第三批.zip`，里面 5 个节点包，另有平台全量表 `D:\交付\全量表.xlsx`。

| 步骤 | 命令 | 看什么 |
|---|---|---|
| 收表迁移 | `migrate_fault_check.py --package "D:\交付\第三批.zip" --product "D:\技能\access-failure-demo" --auto --map "D:\交付\全量表.xlsx" --map-mode all` | 汇总行：`✓` 迁移生效几行、`~` 更新判据几个、`+` 新增、`✂` 删除、"工具链公共文件刷新 N 处" |
| 有失败行 | 按失败清单里附的命令，用 `--only "<包节点名>" --node <节点号>` 逐个补 | 每条补完打印 `✓` |
| 汇报 | 把汇总和失败清单原样列出；按语义匹配的写明对应关系；退回交付方的清单单独列 | |

## 维护（工具链开发者看）

`engine/` 是同一 skills 目录下其他技能文件的副本，让本技能单独安装时也能把旧产物刷到当前版本：

- 平铺脚本：内核库、函数库、调优表导入导出、框架代码、runner、格式检查、共享解析库；
- 整目录副本：`engine/fault-tree-rca/`（含树视图 `render_tree.py`）、`engine/zip2csv/`、`engine/cs-scot-execute/SKILL.md`。

旁边有其他技能时一律先用它们；发行包 cs-scot-generate-optimize 里其他技能都在包根，`engine/` 整个不进包。副本只能由脚本生成，不要手改：其他技能改了文件后跑 `python skills/cs-scot-migrate/scripts/sync_engine.py` 对齐，`--check` 只核对，有差异退出码 1。
