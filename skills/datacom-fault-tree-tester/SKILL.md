# datacom-fault-tree-tester：判断方法验证与交付包生成

## 任务

把用户口头描述的判断逻辑变成三样可交付的东西：符合规范的判断方法文档、能跑的判断脚本、随包的测试数据。全程分 11 步，关键步骤要用户确认，诊断结果必须来自脚本运行，不凭印象下结论。另有一条独立的批量翻新流程，处理存量交付包。

## 术语

| 术语 | 含义 |
|---|---|
| 节点交付包 | 一个故障树节点的交付物 zip：判断方法文档、`判断方法_规范.md`、测试数据、判断脚本、共享解析库、执行记录、本文件 |
| 判断方法文档 | `判断方法.md`，按 `判断方法_规范.md` 写的节点判据说明；节点名称、故障描述、判断条件、命中条件、输出、数据来源六节必填 |
| 判断脚本 | `fault_check_<节点名>.py`，入口函数 `fault_check(data_dir)`，读测试数据目录，返回四态结果 |
| 共享解析库 | `scripts/search_config.py`、`search_log.py`、`search_cmd.py`、`search_diag_txt.py`，配置、日志、命令回显的通用解析函数 |
| 格式检查 | `scripts/check_contract.py`，检查脚本与交付包是否符合约定的格式；`--strict` 时警告也算不过 |
| 四态 | 脚本 `matched` 的四个取值：`true`（查了、确定命中）、`false`（查了、确定没有）、`undetermined`（数据在但判不出来）、`insufficient_data`（没数据可判） |
| 测试数据目录 | 按"网元/CONFIG、CMD、LOG"组织的原始采集文本 |
| 回归基线 | 格式检查在有测试数据时打印的 matched 值与证据数，用于修改前后比对，不评对错 |
| 翻新 | 对存量交付包只修输入输出格式、不动判断逻辑的批量整理 |

## 输入参数

| 参数 | 必填 | 说明 |
|---|:---:|---|
| 故障树节点名 | 是 | 用于文件名和打包输出 |
| 节点路径 | 否 | 根到节点的完整链，`/` 分隔。树上有同名节点时强烈建议提供：写入判断方法的"节点路径"一节，下游迁移与评估无人值守时按路径消歧（见 `判断方法_规范.md` 2.1b） |
| 判断方法 | 是 | 自然语言描述的判断逻辑 |
| 测试数据目录 | 是 | 按下面的结构组织的网元数据；不提供就无法用脚本验证 |
| 解决方案 | 否 | 故障处理方案，不填则跳过方案验证 |

### 测试数据目录结构

```
网元目录/
├── 网元A/
│   ├── CONFIG/        # display current-configuration
│   │   └── *.txt
│   ├── CMD/           # 其他诊断命令
│   │   └── *.txt
│   └── LOG/           # display logbuffer、display trapbuffer
│       └── *.txt
└── 网元B/
    └── ...
```

`display current-configuration` 必须放在 `CONFIG/`，`display logbuffer` 与 `display trapbuffer` 必须放在 `LOG/`。脚本自动识别两种结构：多网元（数据目录下每个子目录是一个网元）和单网元（数据目录下直接是 CONFIG、CMD、LOG，网元名取目录名）。

测试数据是原始散文件（单个或一堆 log、txt、rar、混杂 zip，没有上述分类结构）时先归类：

```bash
python skills/zip2csv/scripts/zip2csv.py <原始目录或包> -o <输出目录>
```

它会自动调用内置的 ifilter 归类，结束时打印的"原始日志目录建议"路径（`formated_result/<网元>/<CMD、CONFIG、LOG>/`）就是本技能要的测试数据目录，直接当数据目录用；顺带转出的 csv 本技能用不上。两条禁令：不直接拿单个包或散文件去跑 `vendor/ifilter.py`（它会把所在的整个父目录连带无关文件卷进来，还会清删其中的 `*_result` 目录，zip2csv 的暂存分支就是防这个的）；ifilter 依赖第三方库、装不上时 zip2csv 会明确报错，此时向用户要已分类的数据，不手工归类。

## 流程

格式校验 → 语义理解 → 数据探索预检 → 确认判断方法 → 脚本生成 → 数据定位确认 → 故障诊断 → 确认诊断结果 → 方案验证（可选）→ 打包前检查 → 打包交付。各步向用户输出的固定格式见 `references/templates.md`。

### 步骤 1：格式校验

检查数据目录是否符合上面的结构，输出发现了几个网元、每个网元三类目录各有多少文件。不通过时逐条列问题与修复方法（如"网元 X 下没有任何数据目录，至少要有 CONFIG、CMD、LOG 之一"）。

### 步骤 2：语义理解

把用户的判断方法与解决方案转成可执行的具体步骤：明确命中条件（什么情况判为匹配），梳理所有关键名词和条件，不理解的名词主动问用户。

### 步骤 3：数据探索预检

判断方法里出现"本端、对端""配对""关联"这类要扫过数据才能确认的概念时，先扫描数据，列出各网元的关键数据项和可形成的配对，请用户确认配对关系是否符合预期。没有这类概念时跳过。

### 步骤 4：确认判断方法

把理解结果结构化输出：每个条件的描述、数据来源（CONFIG、CMD、LOG）、匹配规则（正则、关键字或数值比较）；需要用户明确选择的边界条件；命中条件的布尔表达式；涉及的网元。用户回复 OK 才进入下一步，回复修改建议则调整后再确认。

### 步骤 5：脚本生成

用户确认后必须生成判断脚本 `fault_check_<节点名>.py`，放在本技能 `scripts/` 目录下（与共享解析库同目录，`from search_xxx import …` 才能成立）。脚本要满足十条格式要求，包括：入口函数 `fault_check(data_dir)`；`sys.argv` 与 `print` 只出现在 `if __name__ == '__main__'` 分支；`.txt` 与 `.log` 都要收、大小写不敏感；返回全局形态的四态 JSON；只用标准库与共享解析库；配置解析必须用 `search_config.py` 的函数。十条要求的原文与返回结果的完整格式见 `references/script_contract.md`，写脚本前先读。

生成后必须过格式检查，逐项修到全绿：

```bash
python scripts/check_contract.py <脚本路径> --strict
```

检查项就是十条要求的机械化版本，FAIL 行自带修法提示。完成后输出脚本路径供用户确认。

### 步骤 6：数据定位确认

执行脚本前，先输出已定位到的关键数据（哪个网元的哪个配置项是什么值）请用户确认。发现数据缺失时告知"未在数据文件中找到 X 命令的输出"，请用户说明该命令输出在哪个文件，或直接粘贴数据片段；调整脚本后再确认，循环到定位正确。

### 步骤 7：故障诊断

运行脚本，按网元输出：检测到几个符合条件的情况及各条证据，或未检测到。诊断结果必须来自脚本运行，不为了贴合预期改脚本。

### 步骤 8：确认诊断结果

请用户确认结果是否正确；用户提出修改建议则调整脚本逻辑并回到步骤 6。

### 步骤 9：方案验证（可选）

只在用户提供了解决方案时做：说明方案是否有效及原因，或需要调整的问题与建议。

### 步骤 10：打包前检查

四项必查：测试数据目录存在且有有效文件；判断方法文档已生成且必填字段齐全；判断脚本已生成且复用了 `search_config.py`；格式检查全绿：

```bash
python scripts/check_contract.py <打包目录> --strict
```

有 FAIL 或 WARN 就按提示修完重跑，全绿才许打包。请用户确认四项都通过。

### 步骤 11：打包交付

打包内容清单：

| 类别 | 内容 | 说明 |
|---|---|---|
| 判断方法 | `判断方法.md` | 符合规范的判断方法文档 |
| 规范参考 | `判断方法_规范.md` | 始终包含 |
| 测试数据 | `测试数据/` | 用户输入的测试数据目录，完整复制 |
| 判断脚本 | `fault_check_*.py` | 如有 |
| 共享脚本 | 脚本 import 到的 `search_*.py` | 一律随包，不管本次改没改。包必须自包含，下游只从包里收共享模块，包里没有则迁移后 import 失败。其他有改动的 scripts 下脚本也随包 |
| 执行记录 | `执行记录.md` | 本次使用过程的完整记录，模板见 `references/templates.md` |
| 技能定义 | `SKILL.md` | 本文件，始终包含 |

zip 落在 `skills/datacom-fault-tree-tester/output/<节点名>_<yyyyMMdd-HHmmss>.zip`，名字必须带打包时刻的时间戳。同节点重新打包是新时间戳文件并存，时间戳最大的是最新版；禁止删除或覆盖 output 目录里既有的包，这就是版本历史（要回滚就拿旧时间戳的包重新迁移）。打包后把判断脚本从 `scripts/` 移入交付包，技能目录不留生成产物：`scripts/` 只常驻共享解析库与 `check_contract.py`，历史节点脚本的正本在各自的交付包里。

## 批量翻新存量交付包

用户说"批量优化""翻新旧交付包""把历史包对齐规范"时走这里。目标是让存量包都能跑通：格式校验加脚本输入输出格式对齐。判断方法与判断逻辑的优化不进批量；业务同事点名某节点逻辑有问题时，走单节点流程（步骤 2 到 8）重新生成。

输入：一堆交付包 zip，或整个 `output/` 目录（同节点多个时间戳版本自动取最新；用户点名了就按点名的来）。

硬约束：修复必须逐包手改，禁止写脚本批量改源码。脚本只能做搬运与检查（批量解压、批量跑格式检查、汇总统计、重打包）。要动 `.py` 或 `.md` 的内容就必须逐包打开、读懂上下文、手工编辑，原因有四：

- `return False` 有的是"空数据"分支、有的是"判定确实不成立"，正则分不出，一律改成 undetermined 就动了判断逻辑。
- 文件发现、入口签名、多网元探测在各包里写法都不同，没有可安全替换的统一模式。
- 判断方法文档的"输出"一节要写该节点实际返回什么，套模板等于写假文档。
- undetermined 的 reason 要写这次为什么没数据，逐包不同。

更关键的是批量改会绕过回归保护：第 4 步要求每个包修完重跑检查、且 matched 与修前一致；一次改 N 个包必然跳过逐包回归。包多就按 FAIL 优先、分批做（一批 3 到 5 个包，做完汇总再下一批），用户可随时叫停。

逐包流程：

1. 格式检查：解压到临时目录，跑 `python scripts/check_contract.py <解压目录> --strict`。
2. 全绿则跳过：不重打包，汇总记"已达标"。
3. 有 FAIL 或 WARN 则只修输入输出格式：入口签名改成 `fault_check(data_dir)`；补多网元与单网元探测；文件发现改成 `.txt` 与 `.log` 都收；输出改成全局形态的四态字符串（缺数据 insufficient_data 与判不动 undetermined 分开报）；`sys.argv` 与 `print` 挪进 `__main__`；补齐脚本 import 的 `search_*.py`。按检查输出的修法逐项修，判断逻辑一行不动；拿不准某处算不算判断逻辑就停下问用户。
4. 回归：包里带测试数据的，检查会自动打印回归基线（matched 与证据数）。修完重跑检查必须全绿，且基线 matched 必须与修前一致。唯一例外：三态改四态使 `undetermined` 变成 `insufficient_data`，两者同属"判不了"，下游视为等价。变了就是动到逻辑了，停下问用户。修前就跑不起来的没有基线，只验修后合规。
5. 重打包：新时间戳 zip 落 `output/`，不覆盖旧包；`执行记录.md` 末尾追加"翻新记录"段（模板见 `references/templates.md`）。
6. 汇总：结尾按三类列清单：已达标跳过、已翻新（附修项）、修不动点名（附原因）。

## 判断方法文档怎么写

严格按 `判断方法_规范.md` 生成 `判断方法.md`：

- 必填六节：节点名称、故障描述（一句话说清现象与影响）、判断条件（条件 A、B、C 并行，或步骤 1、2、3 顺序）、命中条件（布尔表达式）、输出（匹配时输出什么）、数据来源（命令加目录）。
- 选填三节只在用户提供了才写：适用产品、示例数据、注意事项。
- 只写用户明确提供的信息：适用产品、适用版本等用户没说就不写；不添加无关内容；不臆测判断逻辑。
- 规范满足不了用户的特殊场景时可以例外，但要在文档里说明：

  ```markdown
  > **例外说明**：此处不符合规范，因为 [原因]
  ```

## 完整例子

用户说：判断"端口 UP/DOWN 频繁切换"的故障；数据目录 `D:\diagnostic_data\Switch01`；解决方案是检查光纤模块和端口配置。

1. 格式校验通过，发现 1 个网元 Switch01，三类目录各有文件。
2. 语义理解后输出结构化的理解总结（条件、数据来源、匹配规则、命中条件），用户回复 OK。
3. 生成 `scripts/fault_check_端口UPDOWN频繁切换.py`，跑 `check_contract.py <脚本> --strict` 全绿，输出脚本路径。
4. 数据定位确认：列出在 LOG 里找到的端口状态变化日志行数，用户确认。
5. 运行脚本，输出 Switch01 检测到的符合条件的情况与证据；用户确认结果。
6. 方案验证：说明方案有效及原因。
7. 打包前四项检查通过，`check_contract.py <打包目录> --strict` 全绿。
8. 打包，输出 `output/端口UPDOWN频繁切换_20260918-103000.zip` 及解压后的内容清单。

## 注意

- 判断方法要具体到可执行；解决方案表述清晰。
- 关键步骤要用户确认，按反馈迭代。
- 诊断结果必须来自脚本运行。
- 严格按 `判断方法_规范.md` 写文档，不自己发挥。
