# Datacom Fault Tree Tester

> 验证你的故障树判断方法能否被 AI 正确理解与执行

## 核心功能

1. **判断方法生成/优化** — 根据用户描述，生成符合规范的判断方法文档
2. **故障诊断** — 可选：用 Python 脚本验证判断方法能否正确执行
3. **方案验证** — 可选：验证故障解决方案的有效性

---

## 输入参数

| 参数 | 必填 | 说明 |
|------|:----:|------|
| **故障树节点名** | 是 | 节点名称，用于生成文件名和打包输出 |
| **判断方法** | 是 | 自然语言描述的故障判断逻辑 |
| **测试数据目录** | **是** | 包含网元数据的目录。网元数据需按 CONFIG/CMD/LOG 结构组织 |
| **解决方案** | 否 | 故障处理方案，不填则跳过方案验证 |

### 测试数据目录结构规范

```
网元目录/
├── 网元A/
│   ├── CONFIG/        # display current-configuration
│   │   └── *.txt
│   ├── CMD/           # 其他诊断命令
│   │   └── *.txt
│   └── LOG/           # display logbuffer/trapbuffer
│       └── *.txt
└── 网元B/
    └── ...
```

> **注意**：`display current-configuration` 必须放在 `CONFIG/`，`display logbuffer`/`display trapbuffer` 必须放在 `LOG/`。

**自动识别**：脚本内部自动检测目录结构
- 多网元结构：`data_dir` 下存在网元子目录（每个子目录为一个网元）
- 单网元结构：`data_dir` 下直接是 `CONFIG/`、`CMD/`、`LOG/` 目录（网元名取 `data_dir` 目录名）

## 执行流程概览

| 场景 | 流程 |
|------|------|
| **有测试数据** | 格式校验 → 语义理解 → **数据探索预检** → 确认判断方法 → 脚本生成 → **数据定位确认** → 故障诊断 → 确认诊断结果 → **打包前检查** → 打包交付 |

## 详细流程（有测试数据）

### 步骤 1 — 格式校验

检查输入目录结构是否符合规范：

```
格式校验通过！
- 发现 X 个网元：网元A、网元B

网元A：
  - CONFIG/ 文件数：X
  - CMD/ 文件数：X
  - LOG/ 文件数：X
```

**校验不通过时：**
```
格式校验未通过，发现以下问题：

[X] 问题 1：网元 [网元名] 下没有任何数据目录
   修复方法：该网元文件夹下至少需要存在 CONFIG/、CMD/、LOG/ 中的一个目录
```

---

### 步骤 2 — 语义理解

深度理解用户提供的判断方法和解决方案：

- 将自然语言转化为**可执行的具体步骤**
- 明确**命中条件**：什么情况下判定为匹配
- 梳理判断逻辑中的所有关键名词和条件
- 对于不理解的名词，主动询问用户澄清

---

### 步骤 3 — 数据探索预检

当判断方法涉及"配对"、"关联"等需要扫描数据后才能确认的概念时，应先进行数据探索预检：

```
数据探索预检：

基于您描述的"[配对规则]"，我扫描到以下数据：
  - 网元A：[关键数据项]
  - 网元B：[关键数据项]
  ...

可形成的配对：
  - 配对1：[条件] → [网元列表]
  - 配对2：[条件] → [网元列表]

请确认这个配对关系是否符合预期？
  [OK] 符合，继续
  [修改] 不符合，修正规则
```

**何时触发**：当判断方法描述中出现"本端/对端"、"配对"、"关联"等关键字时

---

### 步骤 4 — 用户确认（判断方法）

将理解后的判断方法以结构化方式输出：

```
理解总结：

故障树节点：[节点名称]
判断方法：
  1. 条件 A：[具体条件描述]
     - 数据来源：CONFIG/CMD/LOG
     - 匹配规则：[正则/关键字/数值比较]
  2. 条件 B：[具体条件描述]
     - 数据来源：CONFIG/CMD/LOG
     - 匹配规则：[正则/关键字/数值比较]

边界条件澄清（请明确选择）：
  [A] [边界条件描述A] → ?
  [B] [边界条件描述B] → ?

命中条件：[A 且 B] 或 [C]

涉及网元：[网元A、网元B]
```

**请确认判断方法理解是否正确？**
- 输入 **[OK]** 确认，继续下一步
- 输入 **[修改建议]**，我将调整判断方法描述

### 步骤 5 — 脚本生成

用户确认判断方法后，**必须**生成故障诊断脚本：

```
正在生成故障诊断脚本...

脚本要求：

1. **输入参数**：`<data_dir>` 即可，额外参数通过 `sys.argv` 传递（如有）
2. **目录遍历**：遍历网元目录下所有子目录（每个子目录为一个网元）。脚本内部自动检测目录结构：
   - 多网元结构：`data_dir` 下存在网元子目录
   - 单网元结构：`data_dir` 下直接是 `CONFIG/`、`CMD/`、`LOG/` 目录（网元名取 `data_dir` 目录名）
3. **输出格式**：返回 JSON 格式结果
   ```json
   {
     "matched": "true" | "false" | "undetermined",
     "evidence": [
       {
         "type": "ne|interface|port|tunnel",
         "id": "网元名|Tunnel0/0/1|...",
         "matched": "true",
         "data": {
           "source_files": [
             {"file": "CMD/display bfd session all verbose.txt", "line_range": "1-50", "content": "完整命令回显块..."}
           ],
           "matched_items": [
             {
               "name": "TELSPToAcc1",
               "state": "Down",
               "bind_interface": "Tunnel0/0/1",
               "_source_line": "23-28"
             }
           ]
         }
       }
     ],
     "details": {
       "reason": "无法判断的原因（当 matched 为 undetermined 时）"
     }
   }
   ```
   - `matched`：判断结果（字符串类型）
     - `"true"`：故障条件匹配，检测到目标故障
     - `"false"`：故障条件不匹配，未检测到目标故障
     - `"undetermined"`：无法判断，脚本期待入参但实际未传对应入参、或入参类型/值不符合预期、或关键数据缺失
   - `type`：实体类型（ne/interface/port/tunnel 等）
   - `id`：实体标识（网元名、接口名、隧道名等）
   - `data.source_files`：原始证据块，包含文件路径、行号范围、完整内容
   - `data.matched_items`：命中的具体项，关键字段 + `_source_line` 指向原始位置
   - `details.reason`：当 `matched` 为 `"undetermined"` 时，必须说明原因
4. **文件命名**：存放在 `scripts/` 目录下
5. **通用能力复用**：**必须**使用 `scripts/search_config.py` 中的 `parse_config_file()`, `find_config_item()`, `get_group_items()` 函数进行配置解析，**禁止**自行实现配置解析逻辑（详见 `判断方法_规范.md` 附录）

生成完成后，输出脚本路径供用户确认。

1. **输入参数**：`<data_dir>` 即可，额外参数通过 `sys.argv` 传递（如有）

         }

   - `matched`：判断结果（字符串类型）
     - `"true"`：故障条件匹配，检测到目标故障
     - `"false"`：故障条件不匹配，未检测到目标故障

## 判断方法文档生成规范

> 生成 `判断方法.md` 时必须严格按照 `判断方法_规范.md` 的格式要求。

### 必填字段（必须包含）
- **节点名称**：故障树节点唯一标识
- **故障描述**：一句话描述故障现象及影响
- **判断条件**：条件 A/B/C（并行）或步骤 1/2/3（顺序）
- **命中条件**：布尔表达式
- **输出**：说明匹配时的输出结果
- **数据来源**：命令 + 目录（CONFIG/CMD/LOG）

### 选填字段（用户提供了才写）
- **适用产品**：用户明确说明了才写
- **示例数据**：用户提供了才写
- **注意事项**：用户提供了才写

### 禁止事项
- ❌ **禁止自己发挥**：适用产品、适用版本等产品信息，用户没说就不要写
- ❌ **禁止添加无关内容**：只写用户明确提供的信息
- ❌ **禁止臆测判断逻辑**：严格按照用户描述的逻辑生成

### 例外情况
如果规范.md 无法满足用户描述的特殊场景，可以有例外，但需在文档中说明：
```markdown
> **例外说明**：此处不符合规范，因为 [原因]
```

---

## 注意事项

- **判断方法**需足够具体，提供可执行的步骤
- **解决方案**需清晰明了，避免模糊表述
- 关键步骤需要用户确认，根据反馈迭代优化
- 诊断结果必须基于脚本执行，不允许过拟合
- 打包产物统一输出到 `output/` 目录
- **测试数据目录为可选**，但不提供测试数据时无法执行脚本验证
- **严格按照判断方法_规范.md 生成文档**，不要自己发挥
