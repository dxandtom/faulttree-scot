# cs-scot-generate-optimize —— 生成/优化前门(只路由,不干活)

**本文件已加载,不要再次加载或调用本技能。你的任务:按下面的判定表认出输入形态 →
找到对应线的手册 → 照那本手册干活。前门自己不实现任何一步,也不改各线的任何步骤。**

## 一步定线:输入形态判定表(全机械特征,查表不猜)

**判定的是你(模型)不是代码**——前门没有分发程序,是你读这张表照做;各线内部才有真代码
(migrate 分辨单包/合集/对应表、generate 分辨新老格式母表)。所以判定依据一律用**客观可查的
特征**(文件里有没有某列、有没有某文件),**认不出就问人,绝不猜**。

**判定结构(三层,别混):**

```
一条线   = 若干「招牌」的 OR    ← 优化线有 3 个招牌,任一个命中就是它
一个招牌 = 若干「特征」的 AND   ← 特征必须全满足,少一条就不是这个招牌
入参【必需】≠ 招牌              ← 不参与认线,是定线之后的清点清单
```

各招牌的特征(括号内 AND 关系,必须同时成立):

| 线 | 招牌(彼此 OR) | 特征(AND) |
|---|---|---|
| 生成线 | 母表 xlsx | 有层级列 ∧ **无** zip 列 ∧ **无** node_id 列 |
| 优化线 | ①交付包 / ②合集包 / ③对应表 | ①有 `判断方法*.md`(文件名不含"规范")/ ②多个子目录各有一份判断方法.md / ③有层级列 ∧ 有 zip 列 |
| 结构手术线 | 用户明说增删 | 用户明说增/删节点 ∧ 没有交付包 |
| 回流线 | 评估报告/反馈 JSON | 有 `meta.verdict` + `reconciliation`(评估报告)∨ 条目含 `error_class` ∈ 六类名(feedback/失败签名) |

> **招牌内部为什么必须 AND**:母表那三条是**互斥性设计**——只有"有层级列 + 无 zip 列 +
> 无 node_id 列"同时成立,才能与对应表(有 zip 列)、调优表(有 node_id 列)分开。
> 少判一条就会把对应表当母表拿去建树。

**匹配规则:**

1. **认线看招牌——命中一个招牌就定线**,不要求入参齐。看到 `判断方法*.md` 就是优化线,哪怕还不知道
   要装到哪个产物;
2. **开跑看入参——必需项必须全齐**,缺一样**停下问用户要**,别拿默认值硬凑、别自己编路径、
   别在文件系统里瞎找;
3. **多条线招牌同时命中** = 混合输入,不是冲突 → 按 §混合输入的依赖序逐条跑,不要二选一;
4. **招牌一个都不命中** → 响亮问人(把你看到的文件形态描述给用户,请他指认),
   **不许挑一条"最像的"硬走**。

| 招牌输入(认线用,机械特征) | 走哪条线 | 完整入参(跑起来实际要这些) | 手册 |
|---|---|---|---|
| **故障树母表 xlsx**(层级列;无 zip 列、无 node_id 列。新格式多页签与老格式单页签〔`L1(Chinese)` 表头〕皆算,两格式分辨见 generate 手册) | **生成线**:建树→归集→绑定→校验,直出场景技能 | ① 母表 xlsx【必需】② **场景名**(截子树+命名,`--start-node`)【必需】③ 每种指标一份数据(csv/xlsx;裸采集 txt/zip 先转三表)【必需】④ 产物落点 `--out-base`【可选,默认母表旁 `scot技能/<短名>/`】。**唯一不要既有产物的线**——它就是产生产物的 | generate |
| **交付包**(zip/目录,内含 `判断方法*.md`——**这一样就是招牌**,排除文件名带"规范"的)/ 多节点**合集包** / **对应表**(层级列 + zip 列) | **优化线**:判据替换+绑定换血,批量/单包/翻新 | ① 交付包/合集/目录【必需】② **场景产物目录**(`--product`:产物目录,技能形态给它的 `assets/`)【必需,装到哪去】③ `fault_check_*.py`【**包里有则判据+脚本一起迁;没有则只迁判据**,由人改调优表,不是错误】④ 对应表 `--map`【批量模式用;包里自带一张也自动发现】⑤ `--auto` 批量循环【合集包用】 | migrate |
| 用户明说**增/删节点**,且没有交付包 | **结构手术线** | ① **产物目录**(技能形态给 `assets/`)【必需】② 增:父路径 + 节点名 + 判据原文(+绑定)【必需】/ 删:节点名或 node_id + **用户明确确认**【必需】 | 本文件 §结构手术线 |
| **评估反思(cs-scot-reflect)的评估报告/反馈 JSON**(`evaluation_report.json` 有 `meta.verdict`+`reconciliation`;`feedback_to_generate.json`/`failure_signatures.json` 条目含 `error_class` ∈ 六类名) | **回流线**:route_feedback 分拣开票 → auto 票照票执行(migrate/调优表/case_gen)→ 记账 → 全库回归,3 轮熔断转人工 | ① 评估报告或反馈 JSON【必需】② **产物目录**【必需】③ 交付包目录【重迁票要用,有就带上】 | 本文件 §回流线 |

> **一句话记牢:除生成线外,三条线都必须有"既有产物目录"这一样**——它们都是在已有的树上动土,
> 没有它无处落地。用户只丢来一个交付包却没说装到哪,**问他要产物目录**,
> 别在文件系统里瞎找、更别新建一个空产物。

**同是 xlsx 的三分辨**(拿到表先看列,别看文件名):

| 特征 | 是什么 | 去处 |
|---|---|---|
| 层级列,**无 zip 列无 node_id 列**(多页签新格式/单页签 `L1(Chinese)` 老格式皆算) | 母表(业务现网导出) | 生成线入口 |
| 层级列 + **zip 列** | 对应表(平台批量交付) | 优化线批量模式 |
| 带 **node_id 列** | 调优表(产物自带的人机接口) | 不是入口输入;结构手术线/人工小改用 |

**生成 vs 优化的分界=有没有既有产物**:目标目录里有 `tree/*.tree_index.json`(技能形态则看
`assets/` 下)即既有产物——交付包/增删/回流全都作用在它上;没有既有产物,只能先走生成线。

## 手册查找次序(仓库态/发行包态通用)

每条线的手册按此次序找,找到第一个就用(与 generate 内嵌 zip2csv 的查找次序同款):

1. **包内形态**:`<本目录>/generate|migrate/SKILL.md`(发行包把两线内嵌成子目录);
2. **仓库形态**:`<本目录>/../cs-scot-generate|cs-scot-migrate/SKILL.md`(开发态兄弟目录)。

**包内形态的路径换算(唯一一条改写规则)**:子手册命令里的 `skills/cs-scot-generate/`、
`skills/cs-scot-migrate/` 前缀,一律换算成 `<本目录>/generate/`、
`<本目录>/migrate/`(用绝对路径);`skills/zip2csv/` 等素材前缀换算成
`<本目录>/zip2csv/`(素材平铺包根)。除此之外照手册逐字执行,不增不减。

**包内素材(发行包自足,生成线直出完整技能)**:公共素材 `cs-scot-execute/`、
`fault-tree-rca/`、`zip2csv/` 与线目录**平铺在包根**(包根=同门容器,扮演仓库 `skills/`
的角色:generate 的素材查找次序②"同门"命中,migrate 找同门也命中,谁不伸手进谁)——
包内形态生成线照样**直出完整可执行的场景技能**,没有"止于产物形态"的边界。
素材目录只是打包原料:**前门判定表不因此多线**,执行诊断的入口仍在生成出的
场景技能里,不在本前门。

## 混合输入:按依赖序执行,不并行不跳步

固定顺序 **生成 → 优化**(前者的产出是后者的输入):

| 同时给了 | 执行序 |
|---|---|
| 母表 + 指标数据 + 交付包 | 生成线全程(产物落地)→ 优化线迁入交付包 |
| 交付包 + 显式增删指令 | 优化线(**带对应表时**包内新节点自动走增分支;无表的新节点走结构手术线,或让交付方补对应表)→ 结构手术线处理剩余显式增删 |

## 结构手术线(增/删节点,不经交付包)

一切走**产物自带的调优表往返**(export → 改表 → import,校验/台账/孤儿绑定处理全复用):

- **增**:`python "<产物>/scripts/export_tree_excel.py" --out "<产物>"` 导出调优表 →
  新加一行(node_id **留空**自动分配;写清父路径、判据原文、绑定)→
  `python "<产物>/scripts/import_tree_excel.py" --out "<产物>"` 导回。
  有交付包的新节点**别走这条**,交优化线自动建(判据+S 绑定一次带齐)。
- **删**:**必须人确认后才动手**——先向用户复述"将删除节点 X 及其绑定,不可自动恢复",
  得到明确确认 → 调优表删该行 → import。评估反思或任何自动建议的删除,同样只到"点名"
  为止,人点头才执行。
- 改判据/改绑定不叫手术:量大走优化线(交付包),单行小改直接调优表改行 → import。

## 回流线(承接同门 cs-scot-reflect 的评估输出:分拣开票 → 确认门 → 既有通道执行)

**认**(评估反思 skill 的三种产物都认,机械特征):

- `evaluation_report.json`:有 `meta.verdict`(PASS/PASS_WITH_GAPS/PARTIAL_PASS/FAIL/EVAL_ERROR)
  + `reconciliation` 对账块;要处置的条目在 `failure_signatures` / `verdict_detail`;
- `feedback_to_generate.json` / `failure_signatures.json`:条目含 `error_class`(或
  `error_category`)∈ {ENV_FAILURE, INPUT_GAP, BINDING_GAP, KNOWLEDGE_GAP,
  CRITERIA_GAP, VERDICT_GAP}。

**做**——第一个动作就是跑分拣脚本开票,**不许对着 feedback 自由发挥**:

```bash
python "<本目录>/scripts/route_feedback.py" --feedback <评估输出json> --product <产物目录>
```

它机械判定每条 issue 的真因分支(台账反查包/orphan 定位/节点名对时/证据拼装/熔断识别),
开出处置票,分两档:

- **自动迭代档(auto)**:脚本崩溃重迁、孤儿绑定清理、绑定缺失补挂、用例库过期重生成、
  判定偏差修复(修到与判据文档一致)——**循环内直接照票执行,不等确认**;执行完全库
  重跑重评进入下一轮,同节点同类 **3 轮不过由熔断自动转人工**;
- **人工兜底档(fallback)**:环境故障/数据缺失/绑定清除冲突/故障树缺节点/结论归档争议/
  熔断票——自动化本来就无能为力的情况,汇总交人,这是兜底不是主干。

每轮执行完记账:`route_feedback.py --record <票单> --done all --product <产物>` →
产物 `tree/feedback_log.json`(「改了什么」的历史,与评估目录的 round 报告链对账,事后可审计)。

**票 → 通道对照**(本门不新增任何改动能力,执行全走既有工具):

| 票 | 档 | 通道 | 动作 |
|---|---|---|---|
| 类0·脚本运行崩溃 | 自动 | migrate | 重迁该节点交付包(体检+限定范围修复随迁);清单外返厂 tester |
| 类0·环境故障 / 类1·数据缺失 | 兜底 | 人工 | 报错原文/补数据清单,不动资产 |
| 类2·绑定形态不匹配 | 自动 | migrate | 缺的源在用例数据里只有 raw 形态在场(表未供)——有交付包重迁换 S 绑定(fault_check 直接吃 raw);确无包→zip2csv 转表+data_map 映射,或 tester 需求单 |
| 类2·孤儿绑定 | 自动 | 调优表+import | 清幽灵节点残留绑定(票上带绑定所在脚本定位) |
| 类2·绑定清除冲突 | 兜底 | 人裁(无默认) | ①重迁恢复绑定 ②改用例期望——二选一 |
| 类2·绑定缺失 | 自动 | migrate / 调优表 | 有包重迁;无包补绑定行→import,或 tester 需求单 |
| 类3·用例库过期 | 自动 | case_gen | 节点名在树上、只是 id 重排 → 重新生成用例库,别惊动 tester |
| 类3·故障树缺节点 | 兜底 | tester | 增节点需求单 → 回包走优化线收编 |
| 类4·判定偏差修复 | 自动 | 调优表 / migrate | 按证据修到与判据文档一致(绑定错→改行;实现偏离→限定修复);判定标准不许动,疑为期望标错则留证待熔断复核 |
| 类5·结论归档争议 | 兜底 | 人裁(+debate) | 出争议单;SCOT_DEBATE=auto 可拉辩论卷宗辅助;**绝不自动改引擎口径** |

**四条铁则**:

1. **以判据文档为准**:脚本/绑定放开修(修到与判断方法文档一致为止),**判定标准一个字不许动**
   ——要改标准=缺知识,退 tester 改正本;这是防"改判据应试过用例"的命门;
2. **按轮次全量回归**:处置完必须全用例库重跑执行+评估(全库重评即回归),不许只验单用例;
   同节点同类 **3 轮不过熔断**自动转人工(评估侧自动计数)——人工是兜底,不是主干;
3. **评估隔离**:看过 feedback 的会话等于知道该用例答案,**回归验证必须派独立会话**;
4. **留痕审计**:每轮执行自动记账 `tree/feedback_log.json`;兜底票与熔断票必人工,
   自动档只许执行票面起草的动作,禁止越票发挥。

verdict=PASS / PASS_WITH_GAPS → 无事可做;EVAL_ERROR → 评估自身失败,修评估输入重评,
与产物无关。`case_quality`(期望粒度偏粗)转给用例库维护方(重跑 case_gen 可刷)。
tester 已随发行包(包根 `datacom-fault-tree-tester/`),类3/类4 的返厂票在交付环境里
也路由得过去。

## 发行打包(交付平台=一个自包含包)

```bash
python "<本目录>/scripts/package_skill.py"
```

把前门+两线+公共素材合成 `dist/cs-scot-generate-optimize/` 并打同名 zip:
generate/migrate 与素材(cs-scot-execute/fault-tree-rca/zip2csv)**平铺包根**
(包根=同门容器,两线各自按"找同门"命中素材)、
关键文件逐一核验**缺一即响亮失败并清残局**、
`MANIFEST.txt` 记全部文件与来源提交(工作区有未提交改动标 `+dirty`)、zip 可复现
(同一提交两次打包 sha256 一致)。打包是纯复制,不改写任何源文件;输出目录与任何
源目录重叠会**拒绝执行**。本脚本仅仓库开发态可用,发行包内不含它;包的能力边界见上节。

## 红线

- 前门**只路由**:不改各线手册的任何步骤,不合并各线代码,不代替各线校验;
- **认线之后不做手册没要求的预检**:包里有什么、树上对不对得上,是各线第 1 步命令的
  产出,不是你的前置作业(实测:手工预检烧十几分钟,命令本身几十秒);**禁止用
  `python -c`/自写临时脚本解析 tree_index/产物 JSON**(Windows 中文路径必乱码、
  字段靠猜必错)——要看内容用各线脚本的打印输出,不够就把文件路径报给用户;
- 判定表认不出的输入**响亮问人**,不猜、不硬塞最像的线;
- 删除类动作(删节点/删绑定)无论来自谁的建议,**必须人确认**;
- 各线内部的红线(泄题防线、vendor 引擎不改、零三方件、简报不走上下文等)在各自手册里,进线即生效。
