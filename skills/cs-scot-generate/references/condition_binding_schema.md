# 逐条件绑定的格式约定——生成阶段填进 `<ind>_analyzer.py` 的 `CONDITIONS`

本文规定一条绑定怎么写：有哪些字段、每个判断类别接受哪些参数、参数取什么值、哪些写法内核不接受。绑定是把故障树上的一条判据对应到某个数据源的某一列和某种判断类别的结果；生成阶段的模型填写绑定时读本文，产物目录 `scripts/` 下也带一份副本，人工调优时同样按本文写。

整套诊断里随场景变化的部分只有绑定。生成阶段，模型对照故障树条件和各数据源的真实表头与样本（先用 `analyzer.py` 生成概览），为每条判据写一条绑定：选哪个类别内核（A/C/G/D/J/P；内核指 `condition_kernels.py` 里每个类别对应的统计函数，逻辑已经固定并经过测试）、看哪一列、做什么处理变换、由哪个数据源回答、阈值多少；**对不上就如实标为数据不足**。绑定平铺写进对应数据源脚本的 `CONDITIONS` 列表。

早期版本的 B/E/F/H/I 五个内核（差值、占比 TopN、配置检查、信令流程、特征分析）已停用，存放在 `archive/kernels-v1/`（在数通场景判据的全面核查中一次也没有用到；数通指数据通信，即路由器、交换机场景）。新绑定不要再用这些类别：内核会以"已停用"为由明确返回数据不足。老产物自带旧内核的副本，照常执行，不受影响；蜂窝等早期场景确实需要这些内核时，按 archive 目录下的 README 恢复。

脚本运行时，对每条绑定调用 `evaluate_binding(绑定, {源:表}, 源)`，得到一条事实：算出的量、来源信息（provenance）和 `predicate_satisfied`（按字面比较得到的真假）。成立、不成立、数据不足的最终裁决，路径回溯，以及语义是否真正相同（例如 RSRP 与 RSSI 不是一回事，要降低置信度），仍由根因分析（RCA，由 `fault-tree-rca` 完成）负责。

默认套用模板；只有模板不够用（例如"同一列的极差"这种内核没有的算法）才给该条加 `"mode":"custom"`，并在脚本的 `CUSTOM` 里按 id 写一个返回事实（fact）的函数。步骤 3 会用真实数据运行它，写错会当场暴露。

## 一条绑定的公共字段

| 字段 | 说明 |
|---|---|
| `id` | 条件标识（如故障树里的行号或节点名） |
| `node` | 故障树节点名 |
| `node_id` | 该节点在 `tree/<场景>.tree_index.json` 里的 key（形如 `nN`，短，推荐）或 `code`，两种写法都能识别。必填：根因分析靠它把事实挂回树上。不要填节点名；填错或填了不存在的编号，会被当作无主的"孤儿"绑定报出来 |
| `condition_text` | 逐字取自故障树的判断条件（供根因分析复核） |
| `class` | `A`/`C`/`G`/`D`/`J`/`P` 之一，决定用哪个内核（B/E/F/H/I 已停用，见上） |
| `source` | 数据源逻辑名（对应执行时的 `--data <name>=<file>`）；J 类可以为 null |
| `mapping_reason` | 为什么这样对应、语义或单位上有什么差异、为什么判数据不足（必写，供审核） |
| `decision`（可选） | 模型已经判定本条无法机械评估时填 `"insufficient_data"`（或 `"manual"`；也接受 `"not_applicable"`，按数据不足输出）：直接输出该状态，不跑内核、不给判断。比起写一堆 has/lacks/column 再在 reason 里说"数据不足"，这样更诚实，也更快、更短。 |
| `filter`（可选） | 行级预过滤，用于键值形态的窄表（EAV 窄表：一行一个量，如 `DataItem/DataValue/Unit` 这种形状）或"先选中某条命令、某个检查项的行"的情况：先把行缩小到命中的子集，内核再对子集计算。子句写成 `{column, equals:值\|[值…]}` 或 `{column, contains:…}`，多个子句写成列表，关系为 AND。作用于 A/C/G/P（D 类顶层不接受 filter，要把 filter 写进各 `sub` 子绑定；J 类不读数据）；过滤后剩 0 行，表示该指标项本次没有采集，判数据不足（不是"不成立"）。 |
| `extract`（可选） | 单元格内取值，用于"一格里是混杂的文本，要先从中提取出一段值再判断"的情况，作用于 A/C/G/P。二选一：`{"kv": "<键名>"}`（识别「键: 值」「键=值」「键:值」三种写法，值到空白、逗号或分号为止；逗号后面紧跟 3 位数字时当作千分位分隔符继续读）或 `{"regex": "<带捕获组的正则>"}`（取第 1 个捕获组，即正则里第一对 `(` `)` 括起来的部分；没有捕获组就取整个命中）。A 类加 extract，是提取出数值后与阈值比较（`1,234` 这类千分位写法自动归一）；C/G 类加 extract，是提取出值后再做 equals/contains/regex 匹配。提取不到，该行按缺测处理（计入 `nulls`，不当作不命中）；整列一条都提取不到，判数据不足并附样例。正则编译不通过，明确拒收。判据里给出的"关键字"是需要加工的素材，不能原样当正则用：`%u`/`%d` 是 printf 占位符，要先换成 `\d+`；HTML 残留标记要去掉。 |
| 各类别的参数 | 见下表，直接写在同一个对象里，不另嵌一层 |

## 类别 → 内核参数

| 类 | 名称 | 关键参数 | 产出的事实 |
|---|---|---|---|
| A | 阈值比较 | `column`，`op`（`< <= > >= == !=`，`=` 与 `==` 等价），`threshold`，`scope`（`aggregate`/`count_rows`），`agg`（mean/min/max/first/last/sum），`transforms`；可加 `extract`（先从单元格里提取数值，见公共字段） | aggregate 给 `value`；count_rows 给 `count_satisfied`/`ratio` |
| C | 字段匹配 | `column`，`equals`：[值…] 或 `contains`：[子串…] 或 `regex`：[正则…]（任一命中即命中；regex 用 `re.search`，大小写敏感，逐条编译校验，坏正则明确拒收），`match`（`exact`/`contains`/`regex`），`case_insensitive`，`require`（默认 1）；`absent:true` 表示负存在（命中 0 行才算故障成立，与 `require` 互斥；列全空判数据不足）；可加 `extract`（先提取值再匹配） | `matched` 命中行数，加 `total`/`ratio`/`top` 和样例 |
| D | 多条件组合 | `combine`（`AND`/`OR`），`sub`：[子绑定…]（每个子绑定自带 `class`，可以自带 `source`）；`group_by`："<对象列>" 表示同对象关联（按该列分组，每组单独跑全部 sub，任一组全真才成立；sub 不得跨源） | AND：有子条件为 False 则 False，有数据不足则数据不足，否则 True；OR 对称；group_by 给 `matched_groups` |
| G | 日志匹配 | `column`（日志文本列），`contains`：[码/串…] 或 `regex`：[正则…]；其余同 C | 同 C（实现就是 C） |
| J | 人工确认 | `note` | `status:"manual"`，不给判断 |
| P | 成对比较 | `side_column`（分侧列）加 `peer_marker`（默认 `"*"`，含该标记的行是本端），`value_column`（取值列），可加 `extract`/`filter`，`fault_when`（`not_equal` 为默认，两侧不相等算故障；`equal` 相反） | `local`/`peer`/`equal`；任一侧没有值判数据不足（"查不到对端"是判断不了，不是不成立）；一侧有多个不同的值判数据不足（有歧义，先用 filter 缩小行） |

早期版本的 B（差值）、E（占比/TopN）、F（配置检查）、H（信令流程）、I（特征分析）五个内核已停用，存放在 `archive/kernels-v1/`；新绑定用到会得到"已停用"的数据不足。原有用途的替代写法：F 类的"参数=期望值"改用 C 类 `equals`（整格）或 C 类加 `extract`（单元格内的字段）；I 类的 `row_threshold` 改用 A 类 `count_rows`；B/E/H 在数通判据里没有用到，确实需要时按 archive 目录下的 README 恢复。

P 类的使用场景：判据要"查对端，比较本端和对端的某项信息是否一致"（如 MLAG 两侧的 IP、版本、配置是否一致）。数据形态是同一张表里本端行与对端行靠分侧列区分（如 `Object` 列的本端行带 `*` 标记）；要比较的值在 `value_column`（整格）或该格里的某一段（加 `extract`）；一次只比较一项信息，多项信息各写一条 P 类绑定，并用 `filter` 先把行缩小到该检查项。两侧在不同文件里时改用 `pair_from`（见下一节）。

## 参数化查询（`param_from`）与跨源判据

有的判据一步查不完：要先查出一个值，拿它当参数再查下一处（常见情形是「从命令回显里提取出接口名或网元名，再到配置或日志里查它」；命令回显指设备对命令的输出文本）。这类判据写进跨源脚本 `cross_analyzer.py`（步骤 2 组装时自动生成；由步骤 2.5 的「跨源补绑」环节填写，见 SKILL.md；执行时 runner 把全部数据源都传给它）。共有三个机制：

**1. `param_from` 传参链（单跳或多跳）**。声明"参数先到哪里提取"，查询条件里的 `"@参数名"` 占位符整个被替换成提取到的值（可以用在 filter 的值、`contains`/`equals`/`regex` 的目标值里）：

```python
{"class": "G", "source": "config", "column": "level2", "contains": ["mode lacp-static"], "absent": True,
 "filter": {"column": "level1", "equals": "@plink"},
 "param_from": {"plink": {"source": "cmd", "column": "CmdResult",
                          "filter": {"column": "CmdName", "contains": "peer-link"},
                          "extract": {"kv": "Port Name"}}}}
```

- 参数的规格是 `{source?, column, filter?, extract?}`，`source` 省略时取本绑定的 `source`。提取参数用的就是现成的选行（filter）和取值（extract）两层，没有新语法。
- 多跳：参数按声明顺序解析，后面的参数可以引用前面的（在自己的 filter 里写 `@前一个参数名`）。「Vbdif → 它的 bridge-domain 号 → 该 BD 的配置」这样的三连查，就是三个参数按顺序写；只能向前引用，所以不会出现循环。
- 作用域：参数只在本条绑定内可见。D 类的 sub 子绑定自带 `param_from` 时自成作用域（自己解析自己的参数，不继承外层）；外层参数要给 sub 用，就把参数提到 D 类顶层，sub 里只写 `@名`。
- 内核自动执行的检查：参数提取不到，整条判数据不足（附该列样例）；提取出多个不同的值，判数据不足（有歧义，先收紧 filter）；查询条件里用了 `@xxx` 却没有声明、或者声明的引用顺序不对，明确拒收；没写 `param_from` 却在查询里用了 `@xxx`，同样拒收（否则会拿字面的 @ 去匹配，永远不命中，等于错误地排除）。

**2. `expand` 多值展开**。判据要"每个 X 都查"（如「每个 Vbdif 接口都必须配 bridge-domain」）时，给一个参数加 `"expand": "all"`（逐值代入，全部满足才成立；不满足的值列进 `fail_values`）或 `"any"`（任一满足即成立；命中的值列进 `hit_values`）。一条绑定只允许一个参数带 expand（避免组合数量爆炸），展开的值最多 32 个（超过报数据不足，先收紧 filter）。

**3. P 类 `pair_from`（两侧在不同文件里）**。两侧各自「选行 → 取值」再比较，替代同一张表里的 side_column 形态：

```python
{"class": "P", "source": "config_a", "fault_when": "not_equal", "pair_from": {
   "local": {"source": "config_a", "column": "level2",
             "filter": {"column": "level1", "equals": "Nve1"}, "extract": {"kv": "source"}},
   "peer":  {"source": "config_b", "column": "level2",
             "filter": {"column": "level1", "equals": "Nve1"}, "extract": {"kv": "source"}}}}
```

任一侧提取不到值或没有提供该源，判数据不足（"查不到对端"不是"不成立"）；一侧有多个值，判数据不足（有歧义）。`filter` 要写进 local 和 peer 两侧各自的规格里（写在 pair_from 顶层会被明确拒收，不会静默忽略）。另外，filter 的 `excludes` 模式下，过滤列为空的行不保留："不含 X"对空单元格只是形式上为真，留下会把不干净的续行、汇总行混进对端的选择，比出错误的值。

绑定阶段的分工：

- 单源子代理遇到跨源判据，既不勉强绑定，也不能不写，而是写一行标记 `{"node_id":"nN","decision":"cross_source","mapping_reason":"<缺哪一环>"}`。
- 合并脚本 merge_conditions 把标记汇总成 `dispatch/cross_candidates.json`；`make_dispatch --cross` 生成一份带全部数据源概览和知识条目的补绑任务说明，由一个子代理（或主代理）按上面的模板填进 cross_analyzer.py。
- 跨源绑定不进调优表（由工程侧维护）。

## C/G 类 `contains` 目标值的三条规则

违反这三条会造成误报或漏报，步骤 3 的校验器只能给出软告警，所以写绑定时就要遵守。

**1. 每个目标值都必须独立地是"判据成立的充分信号"**：任一目标值命中，都意味着判据确实成立。多个等价的错误码、同一告警名的不同写法，是合法的 OR；字段标签（`CRC:`/`Rx Power`）、命令名、协议名（`LLDP`/`BFD`）、章节标题禁止作为目标值：它们命中了也不代表判据成立，而 contains 是任一命中即命中，一个过于宽泛的词会使整条绑定失效。超短的 ASCII 串（不超过 3 个字符）几乎必然出问题（`"NP"` 是 `"snmp"` 的子串）。

**2. 值否定、值为空这类语义，禁止用 G 类搜子串**（"字段为空/查不到/未建立/状态非 UP"）：标签存在不等于字段为空，文本子串搜索表达不了否定。数据里有带极性的状态枚举列（值如 `Down`/`FAILED`）时，直接绑 `equals` 最简单（状态藏在混杂的单元格里，就加 `extract` 提取出字段值再 `equals`）；没有这样的列，才写 custom（提取值后判空）或 `decision:insufficient_data`。

"负存在"是另一回事（"没有配置 X/未启用 X"，判的是某行内容整个不存在）：这可以判，缺行本身就是证据。绑 C/G 类加 `absent:true`（命中 0 行即故障成立；列全空时内核改判数据不足，不会把"没导出"误判成"没配置"）；"配了 A 但没配 B"用 D 类组合（AND）加一个存在子条件和一个 `absent` 子条件。禁止以"无法确认不存在"为由填 `insufficient_data`：配置源在场时那不是数据不足，而是把确定的证据浪费了（实际运行中曾因此漏掉根因）。

字面模板如下，照抄字段名：子条件列表叫 `sub`，目标叫 `contains` 列表；`sub_conditions`/`target` 这类自造的字段内核不识别，实际运行中有整条绑定因此变成数据不足的：

```python
{"class": "D", "combine": "AND", "sub": [
    {"class": "G", "column": "level2", "contains": ["preempt-mode timer delay"]},
    {"class": "G", "column": "level2", "contains": ["vrrp recover-delay"], "absent": True}]}
```

两个子条件写法相似、极性相反：第一条不带 absent，命中至少 1 行才成立（要求"配了"）；第二条带 `absent`，命中 0 行才成立（要求"没配"）。

同对象关联（`group_by`）：判据要求"同一接口、同一对象上 A、B 同时出现（或配了 A 没配 B）"时，给 D 类加 `"group_by": "<对象列名,如 level1>"`：按该列分组，每组单独跑全部子条件，存在一个组全部满足才成立；整列绑定时"有 A 也有 B 但不在同一接口"的错误确证由此解决。事实里带 `matched_groups`（命中了哪些接口，根因分析可以直接当证据用）。约束：group_by 组合的 sub 不得跨源（各源的行之间没有对齐关系）；组间三态：有组全真则成立；没有全真的组但有组数据不足则数据不足；否则不成立。

**3. 趋势语义（增长、震荡、刷新）看有没有现成的检测码**：判据给出了对应的检测告警或日志码（如 `hwIfMonitorCrcErrorRising`，设备自己已经判过"增长"），绑告警名是合法的；要人比较两次数值的，单次快照数据判不了，写 `decision:insufficient_data`（注明"需两次采样对比"）。

## `predicate_satisfied` 的极性规则

极性指 true 代表什么。**让 `predicate_satisfied` 永远表示"故障成立"。** 树写"某值=坏值才算故障"，绑 `equals:坏值`；树写"参数≠好值才算故障"，本内核集没有 not_equals（早期版本的 F 类已停用），不要绑好值再靠 `mapping_reason` 反推（那样 `predicate_satisfied` 的含义反了，根因分析稍不注意就会判错）：写 custom（提取值后比较）或 `decision:insufficient_data`，注明"≠语义没有模板"。

## 类别是选型的分类，不是六个互斥的实现

类别对应的是故障树的表述方式（树写"日志"选 G，写"字段取值"选 C），便于选型；底层原语是共享的，G 就是 C（同一个匹配内核）。选行（`filter`）、取值（整格或 `extract`）、判定（匹配/absent/阈值/P 类两侧比较）、组合（D）是四个互相独立的层次，按需组合。`require`：A 类的 `count_rows` 与 C/G 类统一为"满足的行数 ≥ require 才算成立"（默认 1）。

## 处理变换词汇（`transforms`）

固定的、可审核的词汇，不写任意代码：`scale:<f>`（乘一个系数，如 `/100` 写成 `scale:0.01`）、`abs`、`neg`、`round:<n>`、`log10`（量级或对数标度的条件用；x≤0 没有对数，该值按缺测/null 处理，不编造值）。

组前缀（`Common:`/`Voice:`/`Interference:`）由列解析器自动去掉（按第一个冒号），绑定里 `column` 写不带前缀的列名即可命中。

## 列解析（机械规则，绑定写错也不会乱配）

顺序：精确匹配 → 去掉组前缀后精确匹配 → 归一化（去前缀、去空格、忽略大小写）后唯一匹配 → 嵌套路径（`A->B->C`）取最后一段。解析不到或有歧义，判数据不足，`resolved_column:null`，不会挑一个相近的列替代。

## A 类 `agg` 的选择（避免"逐周期率"被无加权平均带偏）

`agg:mean` 是无加权平均：对"逐小时成功率"列求 mean 不等于总体率（各小时样本量不同）。树条件多半要的是"存在劣化时段"，优先用 `scope:count_rows`（数有几个周期超过阈值），而不是 `aggregate+mean`；确实需要整体水平再用 `mean`，并且要知道它没有按样本量加权（内核不持有原始样本量，无法加权）。

## 多页签 xlsx（如信令）

一个数据文件有多个页签（NG、UU、汇总……，各页的表结构不同）。`source` 字段填页签名，就指向该页签；不填就用活动页签（文件保存时打开的那一页）。

- 先跑 `python analyzer.py <数据> -o x.json`（多页签时会列出每个页签的列），再加 `--sheet <名>` 看某个页签的详情；
- 条件和组合的子条件各自把 `source` 指向自己的页签，脚本按需加载；同一文件内跨页签的组合在本脚本内就能计算。

## 只绑用得到的列（控制交给根因分析的数据量）

只为故障树真正涉及的判据建 `CONDITIONS`，只绑它要的那一列；表里其它无关字段不要搬进来。生成的脚本只计算 `CONDITIONS`，所以根因分析收到的是"每条判据少量数字"，而不是整张表。这正是把统计放进生成脚本的好处：模型读树和表头时就把用不到的字段筛掉了，根因分析不会被海量数据淹没。

## 全覆盖：遍历每个叶子节点、按树绑定（不要只绑"这次数据里出现的值"）

上一节说"不要多绑"，这一节说"不要少绑"，两者合起来是：本数据源能回答的叶子节点，一个不多、一个不少。

- 数据驱动（绑得不全的最常见原因）：翻这次数据里 `DCInnerCause`/`SgNBAddRejCause` 出现了哪些值，看到一个绑一个，没出现的叶子就不写。后果有两个：一整支故障（这次没出现的码）被漏诊而没有任何提示；脚本只适配本次数据，换一份数据就查不到别的码，违背"一次生成、反复执行"。
- 树驱动（正确做法）：把 `tree_index.json` 里本数据源能回答的每个叶子都走一遍，按树条件要它查的列和值绑一条（C 类 `contains` 那个码），不管这次数据里有没有出现。判据依据是"树的这个叶子要在 `<列>` 里找 `<值>`"，不是"这次出现了 N 次"。
- `mapping_reason` 里不能只拿"出现 N 次"当绑定理由：出现次数是运行时的结果，不是绑定依据。写成"树要 `DCInnerCause` 含 `<码>`，所以 C 类绑该列"，才是按格式和语义写出的、可以反复执行的理由。
- 值这次没出现，不等于不绑，也不等于数据不足：列在本数据源里就照绑，运行时 `matched=0` 表示确定排除（对根因分析来说，比"根本没绑"或"数据不足"有用得多）。`insufficient_data` 只给"查不了"（列或源不在本数据源），不给"查了等于 0"。
- 机械检查（步骤 3 必跑）：`check_tree_coverage.py <tree_index.json> --analyzer <ind>_analyzer.py`，其中 `--columns` 可省，缺省自动读 `overview/<ind>_overview.json` 的列名，不依赖手抄。它按树列出每个没被任何绑定认领的叶子；漏绑（条件正文提到已提供的列却没绑）就是不合格，回去补；"整支未触达/缺源"要逐支确认是确实没有提供对应的数据（信令、配置），还是漏判了一整支。

## 生成要泛化：按"格式加语义"绑，不被这次的具体数据带偏

生成的脚本是一次生成、同场景反复执行（只换输入数据）。所以绑定只应取决于数据格式（有哪些列、量纲、计算方式）和条件语义，不应被"这次数据碰巧缺哪列、值是多少"带偏。

允许的等价重述（应该用，不是替代指标）：节点级"整体有没有失败"（`某流程 Att−Succ>0`），若本数据源有该流程自己的、且同一事件的成功率列，直接用它（A 类，`op <`，阈值为 100 或按量纲定）。这只是把"差值>0"换成代数上等价的"成功率<100"，同一个量、同一件事。例：`RRC建立失败 ↔ SA_RRC Setup Success Rate`、`NgSig建立失败 ↔ SA_NgSig Setup Success Rate`、`QosFlow建立失败 ↔ SA_QosFlow Setup Success Rate`。

怎么算"同一件事"：看该列度量的是什么（建立还是掉线、哪个流程），不看名字。反例：`上下文建立失败(N.UECntx.Est.Att−Succ>0)` 要的是 UEContext 的建立成功率，但本数据源只有 `SA UEContext Drop Rate`（掉线率：建立成功之后才会发生，与建立失败不是一回事），仍然 `insufficient_data`。名字相像不等于同一件事。

绑成功率之前的机械自检，两条都要通过：一，计数器的流程段与列名里的流程词逐字相同（`N.UECntx`→UEContext、`N.RRC`→RRC、`N.NGSig`→NgSig、`N.QosFlow.Est`→QosFlow）；二，计数器不含 `.FailEst.`/`.Fail<原因>`（含了就是特定子因）。任一条不通过，写 `insufficient_data`（或改用 C 类查错误码字段）。

替代指标（禁止），只指这三种：

- 拿通用的或不同流程的率充当"特定失败子因"：`N.QosFlow.FailEst.RNL>0`、安全模式失败、PUCCH 失败、AMF 失败……是专属的子原因，总成功率分不出来（成功率<100% 不等于"是 RNL"），对不上就 `insufficient_data`，不要拿 `SA_RRC Setup Success Rate` 之类凑数。
- 把多条不同的判据绑到同一列：语义错误、条件恒成立、失去泛化。一条判据对不上它专属的量，就是数据不足。
- 树要的原始计数器不在本数据源的列里（如某 `N.xxx` 不在 KPI 导出里，又没有同事件的成功率可以重述）：写 `decision:insufficient_data`（这是格式上的事实，每次都缺，泛化成立），或者指定由有它的数据源回答。

一条通用的判别标准（任何类别、任何场景都适用，不限于某个网元或接口）：一条绑定如果在正常样本上也几乎恒为真，它就分不出故障，是替代指标，不是证据。上面三种之外最隐蔽的一种：拿某个分类列里占比极高（不低于 90%，几乎恒在）的取值充当某个特定子因或信号。正常数据里也是这个值，它根本不区分故障与正常。要确认特定子因，必须对上它专属的列或取值；对不上、或本数据源根本不含那个信号（即使已经确知"本数据源无此信号"，也不要拿相近的高频值替代），就如实写 `insufficient_data`，不要用高频的通用值当作成立。

- 允许的"看数据"只到格式层：看列名、看量纲（0–100 还是 0–1，据此定阈值或 `scale`）、看哪些列存在。不允许因为某列恰好缺失就改判据的语义。也不允许在绑定层判断"某个值存不存在"：概览是截断的（带「词汇不完整」标注的列尤其如此），概览里没看到不等于数据里没有；"有没有"由内核在运行时数出来（见下文诚实性规则第 1 条的"查不了与查了等于 0"）。
- 一句话：同流程同事件的率是重述，应该用；不同流程或通用的率充当特定子因是替代指标，禁止；对不上就如实数据不足。

## 三条诚实性规则（机械层先遵守，根因分析再复核）

1. 找不到列、没有对应的数据源，或者缺原始计数又没有同事件的成功率可以重述：输出 `status:"insufficient_data"` 加 `reason`，不给 `predicate_satisfied`，不编造值。
   分清"查不了"和"查了等于 0"：列在本数据源里，只是树要的那个取值这次没出现，仍然写 C 类绑定（`matched` 自然是 0，即确定排除），不是 `insufficient_data`。`insufficient_data` 只留给"列或源根本不在本数据源"。把"值没出现"当数据不足，等于把一个确定的"不是它"降级成"说不清"。
2. NIL、空值是缺测，计入 `nulls`，不当作"不成立"，也不当作 0。
3. 数据源的指定要诚实：树要的量在别的源（如 RSRP 在 CHR 里而不在 KPI 里），写清 `mapping_reason` 并标数据不足或换源，不拿本数据源里相近的列替代（不要再犯 `SINR→语音用户数` 这类错误）。

## EAV 窄表（一行一个量）与空表的语义

- EAV 窄表：有的数据源不是"一列一个量"的宽表，而是「指标名列 + 取值列」的窄表（如数通 diag 文件的 `DataItem`（282 种指标名）/`DataValue`/`Unit`）。绑法：`filter` 先选中"哪个量"的行，`column` 指向取值列。例：「CPU 占用率>80%」写成
  `{"class":"A","filter":{"column":"DataItem","equals":"SYS_CpuUsage"},"column":"DataValue","op":">","threshold":80,"scope":"count_rows"}`。
- 空表（只有表头、0 行）一律判「数据不足」（所有读表的类别）；`filter` 命中 0 行也判「数据不足」（A/C/G/P），内核自动处理。没有数据不等于排除，不要把 `matched=0/0` 当作"确定不成立"。（非空表上 `matched=0` 仍是确定排除，语义不变。）
- D 类顶层不接受 filter（明确报数据不足，不会静默忽略）：把 filter 写进各 `sub` 子绑定，各自选行再合成。
- 命令回显里计数器判据的规则：「回显里出现某告警名」可以用 G 类（告警名只在发生时出现）；「回显里某计数器>阈值」禁止用 G 类，因为 `CRC:` 这类标签始终存在，值为 0 也会被子串命中（误报）。首选 A 类加 `filter`（选中该命令的行）加 `extract`（`{"kv":"CRC"}` 或正则捕获组）提取出数值再比较阈值（千分位自动归一）；正则或多值语义复杂到 extract 表达不了，再写 custom 并调用 `mo_config.extract_metric`。详见 `references/datacom_log_adapter.md`。

## 一个节点多条判据怎么绑

- 同源多条（尤其是 AND 关系）：优先用 D 类组合成一条绑定（AND/OR 语义由内核合成：有假即假，有缺即缺）。拆成多条独立绑定也支持（同一个 node_id 全部挂上），但辩论复核环节对多条独立事实按"任一成立即成立"合并，AND 节点会被高估；D 类的 `predicate_satisfied` 本身就是合成后的结论，没有这个问题。
- 跨源组合：把各个合取项填进各自数据源的脚本（同一个 node_id），AND/OR 留给根因分析合并（单个脚本只看得到一个数据源）。
- 覆盖度检查（check_tree_coverage）是节点级的：它保证每个叶子至少被认领一次，但"一个节点的第 2、3 条判据有没有漏"没有机械检查。多判据节点用 D 类，就把"绑没绑全"归结到了节点级，覆盖度检查能够发现。

数通「诊断文件包」场景（路由器、交换机的 cmd/diag/config/dblg/log/opr/bas 一组 CSV，配混合格式的故障树，即层级列按新格式、判据挤在一列按老格式）：7 类文件与内核的对应表、EAV 窄表的 `filter` 绑法、命令回显里计数器判据的规则、空表语义，详见 `references/datacom_log_adapter.md`。
