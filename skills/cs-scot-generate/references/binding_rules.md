# 绑定的判断规则与校验警告的处理

本文说明"怎样才算把一条判据绑对"，以及步骤 3 的校验器报出警告后怎么处理。正文 SKILL.md 只给命令和顺序，填写 `CONDITIONS` 或处理校验结果时读本文。类别、字段、参数的精确定义见 condition_binding_schema.md。

## 1. 一条绑定包含什么

一条绑定回答五个问题：这条判据由哪个数据源回答；看哪一列；用哪一类判断（A 阈值比较、C 字段匹配、G 日志匹配、D 多条件组合、J 人工确认、P 成对比较）；判断的参数是什么；为什么这样对应（`mapping_reason`）。参数按类别不同：

- A 类：比较的阈值和方向（大于还是小于）；数值需要先换算的（如百分比转小数），写换算方式。
- C、G 类：要匹配的值（`contains` 或 `equals`）。
- 值藏在单元格一段文字里的，用 `extract` 写明截取哪一段。
- 需要先筛选行再统计的，用 `filter` 写筛选条件。

每条都要填 `node_id`（`tree_index.json` 里的短编号 `nN`），根因分析靠它把事实挂回树上。本数据源确实该回答、这次却回答不了的判据，写 `decision:insufficient_data` 并给理由。

## 2. 绑定是逐条的模型判断，禁止用脚本批量生成

每条绑定都是"读判据原文 → 语义上对应到数据源、列、类别 → 写出真实的 `mapping_reason`"的结果。不要写关键词分类或正则匹配脚本把判据批量翻译成 `CONDITIONS`：那会绕过语义判断，`mapping_reason` 全是模板话，无法审核。子代理失败也不是改用脚本的理由，主代理逐条填。

建树后先核对步骤 1 输出的"带判据节点 N"。N 为 0 就停下报告，几乎可以肯定是判据列没被识别（组装脚本也会拦），不要自己读 Excel 造绑定。

## 3. 按树遍历，要全覆盖

遍历 `tree_index` 里本数据源能回答的每个叶子节点，逐个绑定；按树条件要求的列和值绑（C 类绑 `contains` 那个码），不管这次数据里有没有出现。不要"翻数据里出现了哪些码，看到一个挂一个"：那样会漏掉整个分支，并且只适配这一份数据。

值这次没出现就照绑，运行时 `matched=0` 表示确定排除，不是 `insufficient_data`。`mapping_reason` 不要只写"出现 N 次"，那是运行结果，不是绑定依据。

## 4. 多个数据源都能回答就都绑；多个子条件要绑全

各数据源的子代理互相看不见。"这个大概日志那边会绑"的推让，结果是两边都没绑。本数据源能回答就绑，多源同绑同一节点是期望行为：各出各的事实，主次由根因分析合并。

一个节点的判据常由多个子条件组成（换行、"且"、①②分隔）。本数据源能回答的每个子条件都要绑：单源多子条件用 D 类组合，回答不了的子条件显式写 `decision:insufficient_data`。不是碰到一条就算认领了整个节点。

反过来也不要凑数：明显不归本数据源回答的判据整条不写，不写等于不认领，让覆盖度检查显出真正的漏绑。`decision` 占位只给"确属本源该答、这次却答不了"的条目。对全树一百多条逐条表态过两次，结果都是灾难：回复被截断丢数据，每个节点都被"认领"，覆盖度检查失效，"数据不足"的统计失真。

## 5. 按格式和语义绑，不要被这次数据带偏

- 节点级"整体有没有失败"，若本数据源有同流程、同事件的成功率列，直接用 A 类，阈值按量纲给。这是同一件事的另一种表述，不是替代。
- 特定失败子因的计数器不在本数据源的列里时，写 `decision:insufficient_data` 或换数据源。不要拿总成功率充当子因指标，不要把多条判据绑到同一列：语义错误、恒成立、失去泛化。
- 判别看列度量的是什么（建立还是掉线），不看列名。
- 绑成功率之前先自检两项：流程词逐字对上（UECntx、RRC、NGSig、QosFlow 不互相代替）；计数器不含 `.FailEst.`（含了就是子因，禁止用率）。
- 一次生成要能反复用于不同的数据。

## 6. 先确认数据里的写法再绑值

枚举、消息名这类目标值（C/G 类的 `equals`、键值形态数据源的 `filter.equals`）只能绑数据里真出现过、或概览与枚举清单里有的写法，不要照故障树正文猜拼写。概览可能截断，拿不准就抽取全量枚举核对，见 datacom_log_adapter.md。

## 7. 写完核对覆盖度，不要只数条数

跑步骤 3 的 `check_tree_coverage.py`：

- `❌ 漏绑` 大于 0，表示本数据源能回答的叶子没绑，回去补，不要往下跑。
- 绑定条数为 0 或异常少，几乎一定是按数据挑选或结果没收齐造成的。

`check_tree_coverage.py` 从 `tree_index` 枚举每个应该绑定的叶子，把没被任何数据源认领的全部列出来，即使该叶子的码这次数据里没出现。这是值级告警发现不了的盲区：没绑就没有列，没有列就看不见。

- `❌ 漏绑`（叶子条件正文提到本次已提供的列、本源能回答却没绑）退出码 1，必须回去补绑（值没出现就让它 `matched=0`）或显式写 `decision:insufficient_data`。
- `整支未触达/缺源` 要逐支确认：是确实没提供对应数据（信令跟踪、配置文件没传），还是漏判了一整支。后者归"非典型/其他"或补绑。
- 带 `[跨源候选中]` 注记的未绑节点还在跨源补绑流程里（脚本自动读 `dispatch/cross_candidates.json` 标注），先合并跨源结果再收口。
- 跨源时把各数据源的 `--facts` 都传上，合并判定覆盖度；用过跨源通道就把 `scripts/cross_analyzer.py` 也传进 `--analyzer`。漏传会被点名：跨源的绑定同样认领叶子，漏传会让已绑数偏低、误报漏绑。
- 此时还会输出跨源认领对账（软提示）：各源认领分布、"判据像多个子条件却只有 1 条绑定"、"告警类判据多源在场却只有单源认领"。逐个看一眼，防止"碰了一条就算绑完"和互相推让。

## 8. 校验警告的两级处理（步骤 3 的通过标准）

`validate_conditions.py` 查两类问题：没解析到列却给了判断；数据不足没写理由。并识别三类用替代指标充当的情况：`[流程不匹配]`（如 UEContext 条件绑了 RRC 率）、`[建立配掉线]`、`[子因配总率]`（`.FailEst.` 子因绑了总成功率）。它的"覆盖度告警"是数据值级的：已绑定的列里哪些取值没被认领。

- 必须处理的：三类替代指标、恒成立、同一个值绑到多个节点、过于宽泛的匹配词、方向相反、语义错配、把命令名当信号。每条要么改绑修掉，要么在最终汇报里写明为什么保留（例如该值确属专属信号）。不要用一句"通过（有警告）"带过：曾有被忽略的"同一值多挂"和"泛词 '-'"两条警告，后来一条误排除了整支子叶的确证，一条给节点制造了假冲突。
- 记录即可的：覆盖度告警（数据值级）和 `check_tree_coverage.py` 的跨源认领对账。把汇总原文抄进最终汇报，不逐条表态；叶子级的漏绑由 `❌` 检查兜住。

修复按增量进行：改了哪个指标的绑定，只重跑该指标的 analyzer 和 validate；全部修完后，三条命令全量再跑一遍收口，再进步骤 4。

## 9. 假阳性检验（步骤 3.5，有健康数据时做）

把各 analyzer 对一份同格式的健康设备数据再跑一遍。健康数据上 `status:ok` 且 `predicate_satisfied:true` 的绑定，等于正常样本上也成立，高度可疑，逐条复核。故障语义的判据在健康数据上成立基本就是假阳性，改绑；"是否启用某特性、某配置"这类分支或开关判据在健康设备上本来就可能成立，不算假阳性。这是机械筛查，比任何软告警都可靠。没有健康数据就跳过。
