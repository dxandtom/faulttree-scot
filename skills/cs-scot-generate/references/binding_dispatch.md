# 并行绑定的派发与合并（步骤 2.5 的操作细节）

本文说明步骤 2.5 里"任务说明由脚本生成、模型只负责派发和合并"这套做法的每个环节。正文 SKILL.md 只列命令和顺序，需要知道某个环节为什么这样做、出了问题怎么处理时读本文。

## 1. 为什么要并行、为什么由脚本生成任务说明

绑定是逐条判断：读一条判据的原文，判断它对应哪个数据源、哪一列、哪个类别，再写出理由。一棵树几十到上百条判据，单个会话逐条做既慢又容易在长上下文里出错。所以把判据分成小批，每批交给一个子代理并行做。

任务说明（`<OUT>/dispatch/<指标>_batch<N>.txt`）由 `make_dispatch.py` 生成，而不是模型自己写，原因有三：

- 说明里要嵌入该数据源的概览和枚举原文，脚本能原样嵌入，模型转述会删减。
- 公共规约和 C/G 类、键值形态数据源（EAV）的规则是固定文本，脚本每次生成一致。
- 绑定内容不经过任何模型的上下文：子代理直接把结果写成文件，主代理只跑合并脚本。若让子代理把结果回复给主代理、主代理再转录，同一份内容要过三次上下文，主会话会被撑爆。

## 2. 分派：先决定每条判据进哪个数据源的批次

没有指定归属的判据默认广播到每个数据源的批次里。三个数据源就是三倍的判断量，其中大半是子代理读一遍后发现不归自己、不认领的重复劳动。所以先做一轮分派：

```bash
python "<本目录>/scripts/make_dispatch.py" --out "<OUT>" --route
```

生成分派任务说明（每份不超过 60 条判据，通常一份）。派一个子代理按说明快速判断每条判据可能归哪些数据源，多选，宁多勿漏，拿不准就选全部；结果写到 `dispatch/route_batch<N>_result.json`。收到结果后重跑不带 `--route` 的 `make_dispatch.py`，各数据源的批次就只装归自己的判据。

归属的优先级：知识条目（knowledge.md）里声明的归属 > 分派结果 > 广播。

规矩：

- 生成了分派任务说明，就必须真的派子代理并等结果文件写入，再重跑 `make_dispatch.py`。正常模式下发现分派任务说明存在却没有任何结果，脚本会拒绝生成绑定任务说明。曾有模型生成说明 19 秒后直接重跑，分派白做，判断量成倍回来。
- 确实要跳过分派、按广播派发时，显式加 `--no-route`。
- 分派错了不会丢判据：漏选的数据源由步骤 3 的 `check_tree_coverage.py` 查出漏绑；跨源补绑通道兜住跨源的判据；个别分派结果损坏或缺条目时，对应判据自动回落到广播。
- 分派只决定判据进哪个批次，不是绑定：不写 class、column、mapping_reason。

## 3. 生成绑定任务说明

```bash
python "<本目录>/scripts/make_dispatch.py" --out "<OUT>"
```

为每个子代理生成一份自包含的任务说明 `<OUT>/dispatch/<指标>_batch<N>.txt`：

- 判据自动分批，默认每批不超过 12 条，`--batch-size` 可调。小批有两个好处：子代理最后一次性写结果文件，批太大时这一步要十几分钟且期间没有任何工具输出，会被主进程按"10 分钟无输出"终止；批多则并行度高，总耗时明显下降。
- 该数据源的概览和枚举原文自动嵌入，公共规约与 C/G 类、EAV 数据源的规则是固定文本。
- 键值形态的数据源缺枚举时会拒绝生成，并给出抽取枚举的命令，先补再跑。
- 耗时自动记录：`make_dispatch.py` 记派发时间，`merge_conditions.py` 合并时按文件时间算出每批的绑定耗时，都写入 `<OUT>/timing.json`，供提效汇报使用。

## 4. 派发给子代理

派发提示词只需一句：

> 你的全部任务和材料在 <任务说明路径>，用 Read 读完它（可分段），照其中规约执行；结果写到说明里指定的结果文件；最终回复只报"共 N 条，已写 <路径>"。

规矩：

- 一份任务说明派一个子代理；子代理各写各的 `<本批>_result.py`，互不干扰。
- 任务说明多就分批派发：每批固定 8 个子代理，不足 8 份就一次全派；收完一批再派下一批。总耗时取决于批数：66 条判据 18 份说明，每批 4 个要跑 5 轮，每批 8 个只要 3 轮。
- 不要为省事把多份任务说明合并给一个子代理，那等于分批白做，回复截断和长时间无输出的问题会回来；也不要转述任务说明的内容。
- 子代理读不了文件的环境（权限没配），主代理把任务说明全文读入后原样贴进派发词。
- 任务说明和概览都放在 `<OUT>` 内，不用 /tmp（Windows 上 /tmp 在工作区之外，后台子代理读写会被拒绝）。

## 5. 合并结果

```bash
python "<本目录>/scripts/merge_conditions.py" --out "<OUT>"
```

合并是幂等的，先到先合，不必等全部批次回来。脚本做四件事：

1. 验收：每批结果能被 ast 解析、没有 U+FFFD 乱码；点名 C/G 类缺 `contains` 或 `equals` 的格式错误，以及缺 `node_id` 的条目。
2. 按数据源合并并去重（子代理会把同一段重复写两遍）。
3. 用 ast 定位分析脚本里的 `CONDITIONS` 块，把结果直接写入 `<指标>_analyzer.py`。
4. 写入后做语法自检。

模型不要手工编辑分析脚本，也不要自己写替换脚本：曾出现手工编辑留下多余的 `]` 连续报错五次。

失败处理：

- 脚本输出里列出的缺批、坏批（多为偶发的截断或长时间无输出），用同一份任务说明重派一次。
- 再失败，主会话自己按任务说明逐条绑定，把结果写成该批的 `_result.py`，再跑合并。
- 禁止"取不到就编造占位"：循环生成 `insufficient_data` 占位等于批量制造绑定，每个节点都被"认领"，覆盖度检查对真正的漏绑就失效了。
- 禁止让一个子代理承包全部判据。
- 子代理只写自己批次的结果文件，不要直接改 `<指标>_analyzer.py`：多个代理同时改一个文件必然冲突，合并只能由脚本串行完成。

## 6. 跨源判据的补绑

单个数据源的子代理遇到"先查别处才知道查什么、要与别的源比对"的判据，会按规约写 `decision:"cross_source"`。合并后若打印"跨源判据候选 N 条"，跑：

```bash
python "<本目录>/scripts/make_dispatch.py" --out "<OUT>" --cross
```

生成跨源补绑任务说明，候选同样分批（每批不超过 12 条，`cross_batch1..N.txt`）：27 条塞给一个子代理曾跑了 13 分钟，输出截断、格式损坏，整批返工。一份说明派一个子代理，分批规则同第 4 节，按 `param_from`、`pair_from` 两种模板补绑（模板见 condition_binding_schema.md 的"参数化查询"一节），结果照旧跑合并，写进 `cross_analyzer.py`。

- 跨源批次的结果缺完成标记时，合并脚本会核对"本批候选是否逐条表态"，齐全则接收。禁止手工往结果文件补 `# BATCH_COMPLETE`：那会废掉截断检查。单数据源的批次允许不认领，所以无法用"逐条表态"核对完整性，仍只靠 `# BATCH_COMPLETE` 标记做截断检查。
- 没被任何数据源认领的判据也会被扫进候选。分派上线后每条判据基本只有一次绑定机会，该源不认领就靠这里捞回，这类候选变多属期望行为。
- 顺序规则：先把跨源补绑做完（结果合并进 `cross_analyzer.py`，或确认没有候选），再进步骤 3 的覆盖度收口。在跨源合并之前跑 `check_tree_coverage.py`，"整支未触达"会虚高，不要据此判定分派或绑定出了问题。
