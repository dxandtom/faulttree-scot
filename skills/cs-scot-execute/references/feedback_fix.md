# 用户反馈的处理：定位、分诊、修改、验证

用户指着某个节点说"你判错了""应该是 XXX"时，按下面四步处理。流程固定，判断只在第二步。

## 1. 定位（只查文件，不做判断）

拿节点名到 `assets/tree/*.tree_index.json` 查 `node_id`、判据原文、绑在哪个数据源；从结果根目录 `index.jsonl` 的最后一行找到最近一轮的目录，读该轮 `rca_input.json` 里该节点的 facts，和 `rca.json` 里它的 judgment。

## 2. 分诊（对着字段判断，不凭感觉）

把用户说的"正确答案"与事实对照：

- 答案不在事实里（`resolved_column` 查错了列、`match.targets` 关键词不对、缺失类没带 `absent`、`matched=0` 但 `top` 里明明有……）→ **绑定问题**。
- 答案就在事实里（`hits`、`top`、`explain` 摆着），judgment 或档位却判错 → **判读规则问题**。
- 用户说的是判据本身不对 → **树的问题**。本技能内不改判据文本（改了就与事实对不上），如实告知"回 generate 走调优表重新编译"。
- 事实明确反驳用户的说法时，把 `hits`、`explain` 原文摆给用户看，说明分歧，不硬改。

## 3. 修改

- 绑定问题：改 `assets/scripts/<源>_analyzer.py` 里 `CONDITIONS` 中该 `node_id` 的绑定。绑定是 JSON 数据，改前先读同目录的 `condition_binding_schema.md`；字段写错内核会拒收，正好当护栏。
- 判读规则问题：在 `assets/tree/knowledge.md` 追加条目：`### 标题`，加 `适用:<节点名或判据里真会出现的词>`，再写正文。knowledge 只写判读规则（如"X 出现即成立"），不写结论（如"该局点根因是 Y"）：写结论等于把答案抄进考卷，下次数据变了照样错。

## 4. 分层验证（便宜的必做，贵的不默认做）

- 改了绑定：用上轮 `run.json` 里记的同一份数据，单独跑该数据源的解析脚本 `python assets/scripts/<源>_analyzer.py <数据> -o <临时输出>`，确认该节点的事实变对了（matched、hits、方向）。
- 改了 knowledge：确认"适用"标签能命中该分支，即标签词出现在节点名或判据里。
- 完整重跑（全链加根因分析）不默认做，问用户要不要。

最后汇报：判定是哪一层的问题、依据哪个字段、改了什么、验证前后的对照。
