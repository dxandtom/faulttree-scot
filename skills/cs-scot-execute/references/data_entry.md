# 数据入口：三种数据形态与转换

场景技能收到用户的数据后，第一件事是弄清数据长什么样，再决定怎么喂给执行器。本文说明三种形态各怎么处理、什么情况停下问用户、什么情况继续跑。正文 SKILL.md 只给顺序，数据入口检查报出结果后按本文处理。

## 1. 先跑数据入口检查

```bash
python "<本目录>/scripts/check_data.py" <数据路径>
```

检查脚本判定数据形态（原始采集的网元目录在哪一层、哪些是数据表、哪张只是采集清单），并给出建议的喂法，照抄即可。

- 退出码 0：认得出形态，按它打印的建议喂法继续。
- 退出码 2：结构认不出，或只有采集清单。把报告原样给用户，让用户改目录或确认，不要强行继续。唯一的例外：报告自己指路"疑似原始散文件，先跑 zip2csv"时，照它说的转换，转完重跑检查，仍是 2 才停。

两起真实事故说明为什么必须先检查：`--data raw=` 传错了一层目录，全程"数据不足"；采集清单 xlsx 被当成数据表喂进去，42 个判据一起报"找不到列"。

## 2. 三种形态

### 已解析的表

csv 或 xlsx，表头带 NEName、CmdName、Summary、level1 这类列。按正文第 2 条匹配指标后直接喂。

### 零散的原始文件

单个或一堆 log/txt、rar、混杂的 zip，没有 CONFIG、CMD、LOG 分类目录。检查退出码 2 且连分类目录都找不到，就是这种。同样喂给 zip2csv：它会调用内置的 ifilter 先归类成 `formated_result/<网元>/<CMD|CONFIG|LOG>/`，再转成三张表。此时 `--data raw=` 指向 `formated_result/`（zip2csv 结束时会打印建议值）。ifilter 依赖第三方库，装不上时 zip2csv 会明确报错并给替代做法，把报错原样给用户，不要强行继续。

### 原始日志目录（txt/log）

特征：网元目录下有 `CONFIG/`、`CMD/`（或 `DIAG/`）、`LOG/` 子目录，里面是命令回显的 `.txt`；`.log` 也算原始文本（如 log.log）。先转换再喂，三步都不能省：

1. **转成三张表**，用本技能 `assets/` 里内置的转换脚本：

   ```bash
   python "<本目录>/assets/zip2csv/scripts/zip2csv.py" <zip或目录> -o <输出目录>
   ```

   zip 和目录都可以直接作为输入，目录不用先压成 zip（只有旧版转换脚本只接受 zip，那时才需要 `shutil.make_archive`）。转出的 csv 在 `<输出>/csv/<网元>/LOG|CONFIG|DIAG|CMD/*.csv`，按子目录名对应指标（DIAG 与 diag、cmd 同义，执行器认新旧两种名字）。多个网元产出多份同类 csv 时，保留第一份的表头，其余逐文件追加合并成一份再喂。

2. **无论转换成功与否，把原始目录用 `--data raw=<原始目录>` 一并传给执行器。** zip 输入时原始目录是 zip2csv 输出里的 `extracted/`，目录输入时就是那个目录本身。S 类脚本（`scripts/custom/` 下的节点判断脚本）靠它直接读原始回显；不传，这类节点只能从三张表重建输入，数据不齐时会报"数据不足，脚本未运行"。

3. **转换失败、转出 0 个文件、找不到转换脚本时，明说，但不是停手。** 仍然带着 `--data raw=<原始目录>` 把诊断跑起来：S 类脚本直接读原始文件照常输出事实，执行器对"只有 raw"专门放行；转不出的数据源如实进缺口汇总，结论只代表能看到的部分。只有检查连结构都认不出（退出码 2）才停下问用户。

## 3. 两条禁令

- 不要拿原始 txt 文件的路径冒充某个指标的表去喂。txt 不是表，解析出来是没有预期列的假表，全部判据会错报"数据不足"。
- 数据转换只用本技能 `assets/zip2csv/` 里的脚本。不要去环境里寻找或调用其他技能做转换；找不到脚本就把检查报告给用户。

## 4. 缺口怎么向用户说

带 `--data raw=` 运行时，某一类数据为空，意味着采集数据里不含该类内容。CMD、CONFIG、LOG 的分类是转换器的内部概念，用户上传的是完整的原始包，既不感知分类，多半也补不出来。缺口汇总按"知会"的方式报（执行器已在 run.json 里记 `missing_kind`），不要对这类用户说"缺数据源，请补传"。只有用户直接给了三张表却少了一张，才是"缺数据源，建议补传"。
