# cs-scot-adopt —— 平台脚本收编为绑定纪要

**本文件已加载,不要再次加载或调用本技能;"加载"≠"完成",纪要真正合并进产物才算完成。**

## 它解决什么

故障树判据文本常写得含糊,弱模型据此绑定容易错。但业务平台上**每个节点已有一个验证过的
处理脚本**(python,逻辑精确:查哪条命令、什么状态算异常、现成正则)。本技能把脚本**当规格书
消化**成逐节点「绑定纪要」,随绑定简报下发——绑定的准确率来源从"读懂判据"换成"照抄脚本逻辑"。
注意:**不是跑平台脚本**(平台公共组件本地跑不起来),事实仍由我们的内核计算。

## 前置与输入

- 已走完 cs-scot-generate 步骤 1-2(建树 + assemble 归集),产物目录 `<OUT>` 里有
  `tree/*.tree_index.json`;
- **规则 JSON**(一份或多份):平台导出的 `childrenRule` 列表,关键字段 `nameZh`(节点中文名,
  与树节点名可能有微小出入)与 `script`(平台脚本路径,按文件名对到本地);
- **脚本根目录**:节点脚本 + 公共组件文件夹(公共组件只是被脚本 import,消化时不执行)。

## 流程(四步,机械与判断分开)

1. **机械对齐**:
   ```
   python "<本目录>/scripts/align_scripts.py" --out "<OUT>" --rules <规则json或目录…> --scripts <脚本根目录>
   ```
   名字归一化后精确匹配自动对上;产出 `<OUT>/adopt/adoption_map.json` 与两张残差清单
   `unmatched_rules.json` / `unmatched_nodes.json`,以及消化任务分批简报
   `digest_task_batch<N>.txt`。
2. **残差裁决(模型,量小)**:逐条看 `unmatched_rules.json`——确属某个树节点的
   (如"M-LAG场景的限制"↔"M-LAG场景限制"),把条目**补进 adoption_map.json**
   (照已有条目格式,`"auto": false` 并加一句 `mapping_reason`;**追加到数组末尾,只增量改,
   禁止整文件重写**);确实无对应节点的不动。补完**重跑第 1 步命令**——`auto:false` 的手工条目
   **重跑会保留**(并从残差清单里扣掉),重跑后手工条目排在文件**末尾**、自动条目在前,
   **以打印的统计行为准,别再读文件肉眼核对**;残差裁决只做一轮,别循环。
   **凡是改过 adoption_map(补条目/换脚本/删条目),都必须重跑第 1 步重新分批再消化**——
   消化批的内容是按 map 生成的,map 变了批不变=把旧脚本喂给子代理(第 4 步会按分批快照拦下来)。
3. **消化(模型,分批派发)**:按 `digest_task_batch<N>.txt` 逐批派子代理
   (**一次最多并行 5 个**),每个子代理读本批节点的脚本文件,按简报里的模板产出纪要
   JSON 数组,写到 `<OUT>/adopt/digest_results/batch<N>.json`(末尾带 `# BATCH_COMPLETE`)。
   纪要的灵魂:**命令名/状态字/正则逐字来自脚本**,复杂逻辑(本端对端配对等)标注
   "建议 cross/代理口径",不硬翻;脚本读不懂/纯透传壳的**交 unusable 字段**(不写 digest),
   该节点绑定自动回落判据原文。
4. **校验合并(机械)**:
   ```
   python "<本目录>/scripts/merge_digests.py" --out "<OUT>"
   ```
   编造节点/空纪要/截断响亮拒收;**消化批过期也拒收**(按分批快照 `digest_manifest.json` 校验:
   某节点分批时的脚本 ≠ 当前 map 里的脚本 → 点名"map 改过、批是旧的",重跑第 1 步重新分批再消化);
   合并为 `<OUT>/tree/script_digests.json`;脚本里的 solution 文本并进 `tree/solutions.json`
   (已有不覆盖);对齐了脚本却没交纪要的点名。

完成后**回 cs-scot-generate 步骤 3**(make_dispatch 派绑定):简报会把纪要逐条附在对应判据下
(◆【脚本纪要】,并声明"规格以纪要为准"),批次按字符预算自动变小,不用手调 batch-size。
**两条注入纪律**(实测教训):空壳纪要(unusable)只留档、不注入——零规格不配权威帽子;
「依赖」(平台入参链)只随**跨源补绑简报**下发(param_from 的字段名原料),单源简报不带它
——单源批里它唯一的实测作用是诱发"需上游传参"式投降判词。
**源路由**:纪要声明了 `sources` 的判据**只进对应源的批**(脚本的取数调用=源声明:getCmdPre→cmd、
getCmd(DataItem,本地无此表)→cmd/diag 双标、getCfg→config、getLog→dblg/log),省掉
"每个源都看全部判据"的无用功;没纪要/没声明/
声明与本产物源集对不上的照旧广播,谁能答谁答,覆盖度闸门兜底。

## 纪要不覆盖的节点

树上没配到脚本的判据节点(`unmatched_nodes.json`)走老路:凭判据绑定。两边并存,互不干扰。

## 铁律

- 纪要**只抄脚本里有的事实**(命令/状态字/正则/阈值逐字),不发挥、不编;脚本读不懂/透传壳
  就交 `unusable` 字段(不写 digest),让它响亮地缺着;
- 本地数据是**原始回显/层级配置/日志表**——脚本里的 DataItem 名本地没有,纪要必须落到
  "查哪条 display 命令的回显、看什么关键词"这一层;
- 平台脚本与公共组件**只读不跑**;
- 残差对齐宁缺勿错:配错脚本=给绑定喂错规格,比没有纪要更糟。
