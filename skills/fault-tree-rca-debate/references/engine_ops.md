# 引擎运维说明（已知风险、提速、疑难、机制评测、升级核对）

> 本技能的评分引擎核心在 `vendor/`（评分算法不在本仓库修改，详见 vendor/README.md）。
> 日常使用看 SKILL.md 就够；本文讲更深一层的内容：实际运行中遇到过的问题、调参依据、升级引擎时的核对方法。
> 文中的「执行脚本」指 `scripts/run_debate_rca.py`，即包在引擎外面、负责输入输出、配置映射与调用保护的脚本；「引擎」指 `vendor/` 下的评分引擎；「会话」指运行本技能的 Claude Code 会话（harness），它与引擎共用同一个 LLM 网关。

## 一、已知风险（执行脚本已按这些风险设计，但使用者需要了解）

- **层级偏置（引擎自身的语义，执行脚本无法修改）**：引擎建树时只给第 4 层及更深（L4+）的节点设置 sibling_nodes（兄弟节点列表），第 2、3 层（L2/L3）的节点没有这个键。于是这两层里判据一条都没有匹配上的节点（零匹配节点）走「单节点辩论」（没有竞争辩护、没有兄弟匹配惩罚），在 original 机制下，浅层这些未命中的分支得分会系统性偏高，可能进入 Top-K；softmax/ratio 机制**不受影响**（它们的兄弟分组由 bfs_evaluate 按 parent_code 在所有层级正确计算）。解读 A/B/C 三种机制的评测结果时，要把这一偏置与机制本身的优劣分开看。
- **深度上限 6 层（引擎自身的语义）**：引擎建树只到第 6 层（L6），更深的行会被静默丢弃。执行脚本已加检查：带判据的节点在重新定基（以子树根为第 1 层重新计算深度）后深度大于 6 时当场报错，并提示改截更小的子树；不会不加提示地输出错误结果。
- **文本回声造成的误报**：引擎判断匹配的依据是「判据文本是否包含在 question 里」（question 是执行脚本把 rca_input 里的事实渲染成的一段文本）。执行脚本生成的 question **只复述成立的判据原文**；被排除或数据不足的节点只报节点名。若引擎的 condition_matcher 是语义级（由 LLM 判断）而不是字面包含，这个策略依然安全（宁可少匹配，不错匹配），但 full-match 率可能偏低，观察后可以放宽。
- **确证档（升档规则与手工路径的确证条件相同）**：路径末端的叶子（候选）被 execute 的实测判定为「成立」、是带判据的真实叶子、**且路径上没有实测「不成立/冲突」的上级** → 升入 rca_result；未绑定或数据不足的上级**默认放行**，自动记入 caveats 提示「此处无判断」（全路径都有实测结论并闭环的，单独注明为可信度最高的一种情况）；**上级实测不成立或冲突，即层级矛盾 → 降为疑似**，blocked_at 指认该上级，caveats 写清矛盾所在；候选自身证据冲突（成立与强反证并存）不升档。**升档依据是 execute 的事实，不是辩论得分**。叶子不是真实叶子（截断产生）或叶子未成立 → 留在 probable（截断与实测状态都写在 evidence 的 judgment 上，validate_rca 检查接受这种写法）。回程事实感知（把实测证据回填到 rca.json 的机制，见 SKILL.md「默认开着的优化」）的其余部分：叶子实测成立时 confidence 下限为 medium（托底），被证伪时上限为 low 并附 ⚠ 标记（封顶），blocked_at 点名数据不足的节点，**弃权补充处理**（全场景没有任何成立事实 → 候选降入 undetermined，补上「排序器没有弃权能力」这一语义空缺）。
- **成本**：每条判据 = 1 次匹配 LLM 调用；每个「零匹配兄弟组」（同一父节点下、判据全部零匹配的一组节点）再加（组员数次辩护 + 评委数次打分）次调用，全部串行，引擎内部单次请求超时固定为 180 秒。大树直接跑动辄几十分钟，提速方法见下一节。

## 二、提速方法（实际跑得慢时按这个顺序调）

先认清**成本大头**：不是逐条判据的匹配（线性，约 1 次调用/条），而是**零匹配兄弟组的平方级辩论**——引擎对组里**每个**零匹配成员都各自发起一轮「全组辩护 + 评委打分」（9 个兄弟全部零匹配时约 9×(9+3)，也就是每组 >100 次调用；组内还嵌套 _quick_check_match 重复匹配兄弟判据）。数据没有命中的分支越多，跑得越慢。

0. **并行 + 匹配缓存（提速的主要手段，实现于 scripts/engine_boost.py；默认开 `--parallel 4`）**：
   - 并行：把三处**彼此独立**的串行 LLM 循环（逐条件匹配、逐成员辩护、逐评委打分、逐兄弟 quick check）换成线程池并发，全局并发数由一个信号量限制在 N 以内，嵌套并行也不会超出上限。
   - 缓存（默认开）：同一（question、判据集）只问一次 LLM。引擎在每个零匹配成员的辩论里都会重新检查全组兄弟，这些重复检查全部命中缓存，不再调用 LLM。
   - 语义保证：评分公式与聚合逻辑**逐字复制自 vendor**，并带源码哈希检查——上游发布新版引擎、被复制的方法源码一变，补丁自动跳过、退回串行并打印告警，不会带着过期副本静默运行。实测（用固定应答的假 LLM）：Top-K 与路径得分和串行**逐位一致**，小样本提速 4.4 倍、HTTP 调用从 44 次降到 32 次。
   - N 不要设得太高：与会话共用网关时，并发越高越容易出现 502，推荐 4；`--no-match-cache` 关闭缓存。
1. **`--set K=V` 临时调参（覆盖在 config.yaml 之上，不修改配置文件）**：收益最直接的是 `--set num_judging_agents=2`（每组省 1/3 的评委轮次）；评委输出的 JSON 不稳定时可以调低 llm_temperature。内层重试不必再手动调：LLM 调用保护（见第 4 条）开启时，config 里过猛的 max_retries/retry_delay（如 30 次/15s——重试间隔按次数递增，仅睡眠时间就超过 100 分钟/调用）会**自动收敛**为快失败（2 次/1s），重试全部交给外层退避；用 --set 显式指定的则保留原值。引擎单次请求超时 180 秒是固定值，改不了；`num_debate_agents` **调了不起作用**——引擎按兄弟组成员数起辩护角色，这个配置项不参与。
2. **`--pruned-only`（只在覆盖不全时有效果）**：只把 `rca_input.fault_tree.pruned_nodes`（有事实的节点及其祖先）喂给引擎。**注意**：标准 generate→execute 流水线的覆盖检查强制全部叶子绑定，绑定即有事实 → pruned_nodes 约等于全树，这个开关基本不起作用；只有在局部绑定或覆盖率低的场景走完整形态（rca_input 为完整 JSON 形态）时、或只想跑某个数据源绑到的分支时，它才真正缩小树。在评测用的树上恒不起作用（那些树的判据本来就是从 pruned_nodes 合回来的）。
   语义边界（实测核定）：成立、不成立、数据不足这些**有事实**的节点全部保留，被剪掉的只有**从未被绑定**（uncovered）的分支——漏诊线索仍通过 tree_issues.uncovered_condition_nodes 传递出来，不会丢失。
   两个代价：① Top-K 只在局部子树内排序；② **分数会膨胀**——debate/softmax/ratio 都是兄弟组内的相对量，剪掉兄弟后幸存路径的分数上浮（mock 实测 softmax 0.45→0.63），而 confidence 又按绝对阈值定档 → 开、关两种模式下的分数与档位**互不可比**，做机制 A/B 对比时全程固定一种模式，只用排名指标（hit@k/MRR）。
3. **不要在会强制超时的环境里跑大树**：Claude Code 的 Bash 默认 10 分钟超时，前台、后台任务都受限——大树必然被 SIGTERM 中途杀掉（退出码 143），症状是进程消失、没有 rca 产物、输出停在某个 Debate 中途。要么单开终端手动跑，要么在 `settings.json` 加
   `{"env": {"BASH_DEFAULT_TIMEOUT_MS": "3600000", "BASH_MAX_TIMEOUT_MS": "3600000"}}`（改完重启）。
4. **瞬时 502 不再让整次运行作废（LLM 调用保护，默认开）**：引擎原本的设计是「一次调用把内层重试耗尽 → 置 connection_failed → 整次运行永久降级为关键词匹配」。执行脚本给 LLMClient.chat 套了一层外层重试（3 次，退避 2s/4s，成功即撤销降级标记）——只包住网络传输，不触碰评分算法；`--no-llm-shield` 可以关闭。根本原因仍要处理：会话与引擎共用同一个 LLM 网关时，两边的并发请求挤在一起就容易 502，大树尽量在会话空闲时跑，或错开时间手动跑。
5. **降级要能被察觉**：若 LLM **持续**失败，引擎仍会降级继续跑（匹配的语义已经变了）。执行脚本的检测会打印 ⚠、在 `rca_debate_full.json` 写入 `llm_degraded: true`、在 rca.json 的 caveats 追加说明——看到就修好网络后重跑，不要拿降级结果下结论。
6. **进一步提速需要改算法**：每组只辩一轮、组内成员共享评委打分（而不是每个零匹配成员各辩一轮）、并发调用——这些都涉及引擎核心的执行结构，须与算法上游商定后由上游改版，本仓库不做这类修改。

## 三、疑难速查（实际运行中遇到过的异常日志，每条都有实际复现记录）

- **`LLM调用最终失败: None`（注意是 None，不是网络异常抛出的错误）**：HTTP 200 拿到了响应，但 content 里**没有 text 块**。常见两个原因：一是思考型模型（会先输出思考过程的模型）把 `max_tokens` 耗尽、正文被截断（确保 config 的 max_tokens ≥ 8192，思考型模型给 2000 远远不够）；二是网关高负载时返回空内容或只有思考内容（瞬时现象，LLM 调用保护的外层重试会自动恢复，零星出现属正常）。引擎解析只接受 `type=="text"` 的块，取不到 → 重试耗尽 → last_error 仍是 None → 照样置 connection_failed（与网络断开同样处理，LLM 调用保护会在下次成功时撤销）。跑完看 `rca_debate_full.json.llm_call_failures`：个位数的零星失败可以接受，偏多（如超过 10% 的调用）建议错峰重跑。
- **评委打分出现 `reason="默认分数"`**：该评委的 LLM 调用失败（或 JSON 解析失败），引擎给默认分 `1/组员数`。**单节点辩论组的默认分是 1.0，即满分**——两个评委失败加一个真实评分 0.75，均值能虚高到 0.92（实际运行中出现过）。看到「默认分数」要打折扣地看，不要把默认分当作评委共识；失败次数多的先按上一条修 max_tokens。
- **`检测到API连接失败,自动切换到fallback模式`**：一旦出现，意味着后续所有**条件匹配**都改用关键词而不是 LLM（辩论与评委不受影响，仍会尝试调用 LLM）。本次结果结尾必然带 ⚠ 降级警告与 `llm_degraded: true`——端到端「完整正常跑通」的标准是全程不出现这一行。
- **开跑就成串出现 HTTP 500（而会话走同一网关正常）**：先排除代理问题（输出开头应有 `[net] 已把 LLM 主机加入 NO_PROXY`——执行脚本每次真实运行都会自动设置，不依赖 shell 或会话的代理配置）；然后怀疑**突发并发**：并行默认 4 路，加上会话自身的调用一起挤在同一个网关上，路由器过载常表现为 500。用 `--parallel 2`/`--parallel 1` 对照跑一轮，500 消失即可确认——之后错峰跑，或长期降低并发。持续 5xx 时重试没有用（内外两层重试只能应对瞬时抖动），按 SKILL.md「执行要求」第 5 条停下诊断。

## 四、三种得分机制 A/B/C 的一键对比评测

```bash
# 先用 --engine mock 验证流程，真引擎就绪后换 --engine real：
python skills/fault-tree-rca-debate/scripts/ab_test_mechanisms.py --engine real --k 3 \
    --suite <带答案场景目录> --trees <树索引目录> \
    [--only synth_中]   # 先用小树标定成本，再跑全量
```

数据集：原配的 `cs-scot-eval/suite_real` 30 个冻结场景已随 cs-scot-eval 技能从本仓库移除，现在需要自备带标准答案的场景，用 `--suite/--trees` 显式传入（目录结构见脚本 docstring）。

**指标选择（重要）**：机制对比用**与档位无关的排名指标**（hit@1 / hit@3 / MRR / FP 进榜，FP 进榜指不该报的节点被排进了 Top-K）。四档打分（要求确证根因落在 `rca_result` 档）用在本引擎上要谨慎解读：引擎是纯排序器，升档凭 execute 的事实（候选自身实测成立）——四档分数衡量的是「排序器 + 事实升档」的组合效果，与三种机制哪个更好是两个问题，不要混在一张表里下结论。

真值是「不报根因」的场景（excluded/honest），排序器在结构上做不到（没有弃权能力），工具把它们单列为「弃权能力缺口」——这是全盘替代手工路径要付出的语义代价，与机制优劣分开看。

成绩必须标注 `engine=debate`，与模型手工 RCA 的成绩分表呈现。

## 五、切换与回退

- 用辩论引擎：runner 之后跑 `run_debate_rca.py`（见 SKILL.md）。
- 回到手工路径：照旧用 `fault-tree-rca` 技能产出。两者写同一个结果目录的 `rca.json`、过同一个 `validate_rca` 检查、被同一套评估打分——**保留手工路径作为基线**（难度一 100% / 纠错 73%），引擎在评测中胜出后再考虑「全盘替代」。

## 六、引擎升级核对清单（vendor 换新版时跑一遍；当前版本已逐条核对完毕）

接口假设逐条验证；不符时只改 `run_debate_rca._load_processor` 一处（或新建 vendor/bridge.py）。

| ① | `FaultTreeProcessor(EvaluationConfig)` / `load_fault_tree(path)→df` / `build_tree_structure(df)→tree` / `find_top_k_paths(tree, question, k)→(orig, softmax, ratio, debate_records)` | 直接试跑一次 | 改 `_load_processor` 与调用它的三行 |
