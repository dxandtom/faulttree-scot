# 根因分析规则（fault-tree-rca，与指标无关）

本技能只做一件事：拿故障树和已经解析好的各路事实，判定根因（根因分析，RCA）。它不关心指标具体是什么，今天是这几个指标，明天可以是任意新指标，下面的规则对所有指标一视同仁。

## 1. 输入

- `fault_tree_md`：故障子树（`#/##/###` 层级，标题下是该节点的判断条件；人工编写，可能不规整）。
- `indicator_results`：字典，键是指标名，值是该指标已解析好的事实（只有数据，没有判断）：每个字段或项的真实分布、数值摘要或取值。注意：有的指标提供的是定义或规则（某量怎么算、阈值是多少），不是实测值。定义不是测量。
- 多数情况下每个指标的结果是逐条件事实，形如 `{indicator,source,summary,conditions:[{id,node,condition_text,class,mapping_reason,fact}]}`
  - `fact.predicate_satisfied` 是只在解析到的列上做的字面比较；`fact.status` 可能是 `insufficient_data` 或 `manual`。
  - 这是输入证据，不是最终结论：① 要看 `mapping_reason` 判断语义是否真的相等（如用 RSSI 替代 RSRP、单位不符，就要降低置信或判数据不足，不能因为 `predicate_satisfied:true` 就当成立）；② `fact.status` 为 `insufficient_data` 或 `manual` 的节点判"数据不足"；③ 跨源组合（同一判据的合取项分散在不同指标结果里）由本技能按 AND/OR 合并；④ 路径回溯与数据不足的传播也由本技能完成。字面为真不等于该条件成立。
- 输入可能已被压缩成局部子树：`fault_tree` 含 `outline`（`id→粗状态` 的紧凑导航，很小）、`pruned_nodes`（相关节点：`name/parent/level`，事实挂在 `facts` 里，另有 `condition`、`combine`、`pass_through`、`is_leaf`（是不是叶子）、`uncovered_children`（下面带条件却没人绑定的子因））、`tree_issues`、`unmapped_facts`、`uncovered_values`（判别列里出现却没被任何绑定认领的取值和条数，据此把漏绑的记录归到保留的"其他"类节点，见第 4 节"覆盖度补漏"）。没有 index 时退回 `fault_tree_md`。两种形态规则相同。
  - 输入可能很大，不要一次性把整个 rca_input 读进上下文（会超长报错）。候选枚举与成品拼装都交给代码：先跑 `scripts/draft_rca.py <rca_input.json>` 生成候选清单（成立节点已列成候选，路径、证据、`how` 已预填），本技能只写小裁决单 `decisions.json`（每个候选一条 verdict 和理由），再由 `scripts/finalize_rca.py` 机械合成 rca.json，不手写 rca.json。合成脚本带结构检查：候选漏裁决、确证路径带反证或冲突或存疑（祖先"数据不足"不拦，自动记入 caveats）、排除没写 reason、有成立事实的候选放进待确认，一律拒收。裁决时要看细节用 `scripts/rca_query.py` 抽查（`--node nX`、`--outline`、`--holding`）。不要自己写脚本硬算。
  - `outline` 的粗状态（`成立/不成立/数据不足/未覆盖/免检`，定义见输入自带的 `outline_legend`）只是导航，仍要按 `pruned_nodes` 的条件和事实重新判断，不能拿粗状态直接当判决抄。「成立」表示有正向证据，这类节点不许丢进待确认；「免检」表示高层分类节点不参与判断，不是"检查通过"。
  - `node_id` 是短 id（`nN`）；`pass_through:true` 的节点（汇总、"测试"之类）永不阻断路径；`combine` 是 `AND/OR/unknown` 提示。
  - `node_id` 是权威编号：`Fault_tree_path` 只用 `pruned_nodes` 里真实存在的节点；`tree_issues.orphan_node_ids` 和 `unmapped_facts` 是绑定填错的信号，不据此硬判。
- `knowledge`（可选）：业务同事手写的外挂知识条目（`[{title, 适用?, text}]`，已按当前分支与 `阶段:诊断` 标记筛过，绑定期的经验知识不会出现在这里）。它是判读规则，不是事实，两条用法规则：① 可以相信它说的"怎么查、怎么解读、什么算正常"：知识说某现象属正常（如双活网关一台 ping 不通），对应候选按知识处理，并在 caveats 或排除理由里引用知识标题留痕；知识讲了查询方法或主次规则，照它解读事实。② 不许拿知识顶替实测：知识描述的现象或数值不能当 `actual` 引用，"知识说会这样"不等于"数据里查到了"，成立仍要事实，缺数据仍是数据不足。知识与事实冲突时以事实为准，并在 caveats 写明冲突。

## 2. 通用判定规则（不分指标）

对故障树的每条判断条件，照此四步：

1. 看清这条条件要的是哪个量、字段或取值（记作 X）。
2. 到 `indicator_results` 里找 X 的实际值：找到 X 的实测值，代入条件的阈值、比较或算术，判"成立"或"不成立"；没找到（没有这个字段；某指标只给了 X 的定义或规则而不是实测值；X 要的数据这次没提供），判"数据不足"。
3. 不拿别的量 Y 顶替 X：条件要 X、手上只有相关的 Y，不能用 Y 算个数就声称 X 成立。"有定义"不等于"有测量"，"有旁证"不等于"该条件成立"。
4. 精确匹配：条件点名的取值或标识要精确命中，差一个字符就是没命中（判数据不足），不用相近值顶替。

## 3. 字段映射规则（树里的量对应数据列）：显式、按语义、可审、不编造

真实数据里名字对不上是常态：树的条件常用英文或代码名（如 `SUSRLastAvgRsrp`、`SA_QosFlow_Setup_Success_Rate`），数据列却是中文（如 `上行RSSI均值`、`SA_QoSFlow建立成功率(22B)`）。所以第 2 节的第 1 步"找 X 的实际值"必须先显式建立映射。这个映射在生成阶段绑定时就已建立，理由写在绑定的 `mapping_reason` 里并随事实带进来；本技能在裁决时复核它是否站得住，规则如下（完整形态下模型自己找列时同样适用）：

1. 按含义映射，不按字符串：在数据列里找"语义上就是这个量"的列，理由要让人能复核。现行流程里 evidence 的字段由 finalize_rca.py 从候选清单逐字照搬（node、node_id、condition、actual、how、judgment 及冲突相关字段），模型写不进 `mapping` 之类的额外字段；对映射有疑问，写进裁决单该候选的 `caveats` 或 `reason`，或用裁决单的 `overrides` 把该节点的 judgment 改成"语义近似/存疑"。
2. 找不到就判数据不足，不抓一个相关列顶替：没有"就是 X"的列（如树要 SINR、数据里根本没有 SINR 列）就是数据不足。最隐蔽的错误是把 SINR 映射到"语音用户数"这种只是恰好相邻或相关的列：映射一旦错，后面的数照样算得出，结论却全错且不报错。宁可数据不足，不硬认。
3. 语义或单位近似要标注并降低置信：只有"相近但不等"的列（树要 RSRP、数据只有 RSSI；或量纲、定义不同，如本应是 dBm 的列取值是 0.01/154 这种）可以暂用，但绑定的 `mapping_reason` 必须写明差异，裁决时用 `overrides` 把该节点的 judgment 改成"语义近似/存疑"（低置信），不当作干净的"成立/不成立"。有实测数据的节点不要写"数据不足"，那是对数据是否存在的谎报，真缺数据才叫数据不足。
4. 成功率与原始计数：树要 `尝试-成功`（差值）而数据只有百分比成功率、没有原始计数，要么判数据不足，要么用"成功率<100%"重述同一问题并在 `mapping_reason` 写明这是替代表达，不得假装算出了差值。
5. NIL 或空值等于缺测，判数据不足（对该单元格或该行），不当作"条件不成立"，否则把"没测到"悄悄变成了"正常"。解析事实里每列带 `nulls` 计数，缺测是显式可见的。
6. 阈值出处：按故障树写的阈值用（那是现有权威）；树未标注出处时，在 judgment 注明"阈值取自故障树、出处未核"，不当作已验证的门限。
7. 数值阈值条件怎么判：A 类事实给的是内核按阈值算好的结果（`aggregate` 给 `value`，`count_rows` 给 `count_satisfied` 和 `ratio`，另带 `n_rows`、`nulls`、`valid`），`predicate_satisfied` 已经比过阈值；十分位 `deciles` 只出现在概览工具 `analyzer.py` 的输出里，事实里没有，不要引用。够不够判一条成立由本技能按比例决定，但所引用的数必须逐字来自事实。事实可能带 `hits`（命中原文片段，代码在命中位置截取的窗口）：要在 `actual` 或报告里展示"数据里那一行长什么样"时，只许逐字抄 `hits`（或已含它的 `explain`），不自己从数据里回忆或拼装原文。
8. 看分量，不只看"在场"：C/G 字段匹配的事实带 `total`（纳入的非空行数）、`ratio`（matched/total）、`top`（同列取值分布）。`matched=87` 必须结合 `ratio`（占多少）和 `top`（其他错误码各多少）判主次：`87/90` 是主因，`87/50000` 多半是噪声；排序和置信据此定，不拿裸 `matched` 当强证据。反过来，某取值占比畸高（≥90%、近乎恒在，正常样本里也是它）同样坐实不了特定子因，它不区分故障与正常，顶多当背景，不据此判 confirmed。

## 4. 四档定档：confirmed、probable、undetermined、excluded

一条候选是从某叶子回溯到根的路径。不管判到哪一档，都要把理由说清。各档严格程度不同：

- **confirmed（确证），严格**：终点必须是叶子（`is_leaf`），且根到叶路径上每个带条件的节点都干净成立（没有数据不足或不成立）。成立的中间节点不等于根因（没有 `is_leaf`，或带 `uncovered_children`，最多 probable，写"已定位到该层、叶子因待定"）。必须摆出完整的 `evidence_path`（每个节点：条件、实际值、判断）。
- **probable（疑似），宽松，交给本技能判断**：路径里有"数据不足"甚至"不成立"的节点都允许，只要叶子或关键节点有正向证据、仍值得怀疑（那个"不成立"可能只是数据缺口或绑定造成的假象）。但必须说清为什么只是疑似：`blocked_at`（卡在哪个节点）、`caveats`（上游为何不确定）、`support`（支撑它的正向证据和有效样本量）。理由不清就不合格。
- **excluded（排除）**：有把握这条路确实不通（可靠的"不成立"、无反证），一句话带过，不进列表。但排除的分支里若有节点带"成立"事实（如背景值、泛词命中），这一句话必须点名该节点留痕。裁决单里 verdict=excluded 加 reason 会由 finalize 机械生成这句话；无声略过做不到，候选漏裁决时合成脚本直接拒收。
- **undetermined（待确认）**：既无正向证据、又缺数据。有正向证据（哪怕只定位到中间层，如某计数器 87 条命中）就该进 probable，不放这里。有 `ok+成立` 事实（outline 粗状态为「成立」）的节点，不得作为待确认的阻塞点、理由或观察：它有正向证据，按定义不属于这一档，应升 probable，或有反证、属背景噪声时走排除并在 `excluded_note` 点名。"具体证据待查"不是合法理由：证据已经在输入里，用 `rca_query --node nX` 拉出来判断即可，"待查"等于"没查"，属于工作没做完，finalize 会直接拒收。哪怕只命中 1 条也是成立：判据原文没写数量要求时，1 条命中就是条件成立（存在性语义，内核就按这个判），"只搜到一条、大部分行都不是"不构成待确认或降档的理由，日志里的故障行本来就是少数。
- **诚实底线（任何档都要守，脚本会检查）**：`成立` 的判断必须对应一条真实的成立事实；不给"未覆盖/无 `facts`"的节点编一个"成立"（局部子树已用 `is_leaf`、`uncovered_children`、有没有 `facts` 标出谁没数据）。编造不是泛化。

硬性的只有这几条状态规则：confirmed 要求候选自身成立且路径上没有不成立、冲突、存疑；祖先的"数据不足"不拦，因为查不了是零信息，不当作反证，上级节点是否成立由下级节点的事实自下而上推出，finalize 自动记入 caveats 留痕；有不成立就 excluded。其余全靠本技能判断：

- 哪些路值得报"疑似"、信心多高（high/medium/low）、怎么排序、写什么 caveat，由本技能决定，脚本不限制强度。
- 逐叶穷举，不过度合并：数据里每个有正向事实（matched>0 或命中）的不同叶子或失败模式，各自报一条（confirmed 或 probable；实在闭合不了至少进 `undetermined.observed` 逐条列出）。不把几个不同叶子并成一条，也不只挑最强的一两条：聚合数据常多种失败模式并存，尽量覆盖全。每条各自给真实事实和 caveat，宁可多列几条带 caveat 的疑似，不为凑数编节点或编成立。
- 覆盖度补漏，不让"没绑上"的记录漏诊：输入的 `fault_tree.uncovered_values` 列出了某判别列里出现过、却没被任何绑定认领的取值和记录数，这通常是生成侧漏绑了某一支。即便绑定漏了，也要据这些原始取值把记录归位：剪枝保留了该支的"非典型场景/其他"节点（在 `pruned_nodes` 里），按那个真实节点报一条（闭合不了就 probable 或 `undetermined.observed`），`actual` 附上原始特征码（如该 DCInnerCause 值和条数）。这正是"绑定错了、根因分析仍据事实补救"的地方，不因为没人绑就当这些记录不存在。
- 疑似必须诚实披露：卡在哪个节点（数据不足）、叶子证据是什么、有效样本量和空值比例（如"96% 满足，但仅 1814/20496 非空"）、为什么仍只是疑似。
- 不为了凑 confirmed 编节点或改路径：路径只能用真实存在的节点；有数据不足的节点就老实放 probable，不造"测试""xx排查"之类不存在的节点把路凑完整。
- 疑似不等于确证：不把疑似说成"已定位根因"；它是"证据强、但路径未闭合（上游缺数据）"。

诚实底线由 finalize_rca 的结构检查在合成时保证（确证要求候选自身干净、路径无反证、冲突、存疑，祖先"数据不足"豁免并自动记入 caveats；evidence 逐字来自候选清单；候选不许无声消失；排除必须写理由）。合成报错就改裁决单重跑，不凑路径、不造节点、不绕过合成脚本手写 rca.json。合成成功即交付，不需要再跑 validate。

## 5. tree_issues（顺带把子树的问题报出来）

输入带 `tree_issues` 时，在输出的 `tree_issues` 字段原样带出，可以补充：`uncovered_condition_nodes`（有条件却没人绑定或没有数据源的节点）、`orphan_node_ids`（绑定填了不存在的节点）。这是给人改故障树或补数据的线索，不影响根因判定。

## 6. 同节点多源事实的合成

多个数据源同时绑定同一节点是期望的行为（防漏），合成看要件覆盖（语义判断，由本技能做）：

- 判据的全部要件都被 `ok+成立` 的事实覆盖（单源 D 组合覆盖全条，或多源各证各的要件），节点成立；
- 其他源的"答不了、没查到"（insufficient）不构成阻塞：那是没来作证，不是反证，不据此降档；
- 要件有一块没被任何 ok 事实覆盖，只有那一块算数据不足（对照判据原文数要件，不看"有没有 insufficient 事实"）；
- `成立` 与 `不成立` 并存时，先看不成立那条是什么类：存在类（C/G 非 absent）的未命中是弱阴性，只说明"那份数据里没看见"，不构成反证（告警表命中 2 条、日志表 0 命中，告警存在，成立；caveat 提一笔即可）；A 阈值、P 成对、absent 缺失类的不成立才是强反证，是真冲突，权衡后写 caveat。候选清单已按此分类（弱阴性带 `other_source_note` 留在候选，强反证进冲突区）。

局部子树形态下，剪枝已把"已确立节点"的 insufficient 事实剔掉；完整形态（`fault_tree_md` 加 `indicator_results`）按本节自行合成。

## 7. 输出格式

```json
{
  "rca_result": [ {"Root_cause":"…","Fault_tree_path":["…"],"node_id":"<候选自身的 node_id>","support":"…",
     "evidence_path":[{"node":"…","node_id":"…","condition":"<逐字取自故障树>",
        "actual":"<逐字引用事实(可引 hits/nulls);没有写'事实中无此值'>",
        "how":"<怎么判的,一句人话——事实里带 explain 就逐字抄它(数字与规则不许改写),没有才按事实字段自己拼:在哪个数据的哪列找什么/算什么、实际得到多少、按什么规则判的>",
        "judgment":"成立/不成立/数据不足"}]} ],
  "probable_causes": [ {"Root_cause":"…","Fault_tree_path":["…"],"node_id":"<候选自身的 node_id>","confidence":"high/medium/low",
     "blocked_at":"<卡点:路径反证/冲突、未闭合的子因,或自愿降档时的存疑点>","caveats":"<有效样本量/空值比例/语义近似等>",
     "support":"<叶子证据>","evidence_path":[ …同上结构… ]} ],
  "undetermined": [ {"Fault_tree_path":["…"],"blocked_at":"…","reason":"缺哪个量","observed":["…(仅观察,非根因)"]} ],
  "tree_issues": { "uncovered_condition_nodes":[…], "orphan_node_ids":[…] }
}
```

- 每条 evidence 把条件、实际值、怎么判的（`how`）、判断写全；`pass_through` 的中间节点注明"无独立条件"。这些字段由 finalize_rca.py 从候选清单逐字照搬（冲突时另带 `conflict_actual`、`conflict_how`，弱阴性另带 `other_source_note`），模型不能增删字段；顶层的 `node_id` 是候选自身的编号，评估对账用它。
- `how` 是给不懂技术、不懂判据分类的人看的（报告和 HTML 直接展示它）：事实里的 `explain` 字段就是机械拼好的这句话，逐字抄、不改写数字；它说清"在哪找什么、实际多少、按什么规则、结论"，人对着它就能自行核验判断对不对。
- 给人看的字段用名字、不用 id：`Root_cause`、`support`、`caveats`、`blocked_at`、`reason`、`observed` 一律写节点名字（必要时写成 `名字(nN)`），不只写裸的 `nXX`，人读报告不该还得去翻 tree 文件查 id。只有 `evidence_path` 里 `node_id` 填 nN（同条目 `node` 填名字）。
- 文字与 JSON 一致：`rca_result` 是 `[]` 就不说"发现了 N 条根因"；疑似就叫疑似。
- `rca_result` 为 `[]` 很正常（上游话统、信令缺数据时）；强证据放 `probable_causes`，不硬塞 `rca_result`，更不造节点凑路径。
- 疑似档的要求：每条疑似都应有实际卡点（层级矛盾即上级实测不成立或冲突，机械降档，`blocked_at` 与 note 已预填；候选自身冲突权衡后未升；或语义存疑并写明）。没有卡点的该升确证；未绑定或数据不足的上级默认放行，不是留在疑似的理由。不把确证藏进疑似躲避审查，也不拿疑似档当候选对账的出口（finalize 会直接拒收）。全成立却放在疑似属于规则不符：凭主观怀疑降档可以，但怀疑必须落到具体节点（该节点 judgment 写"语义近似/存疑"（有数据）或"数据不足"（真缺数据），`blocked_at` 写实）；"单源/保险起见"不是降档理由。条目按 confidence 从高到低排；文字汇报详述 high 和 medium 的前几条，low 的合并成一行一条的简表，JSON 一条不少，减少的只是噪音。
- 排除的合法依据（`excluded_note`）：排除一个"判据成立"的候选，合法依据只有两种：① 反证，该节点有 `ok+不成立` 的事实；② 绑定质量问题，点名具体是哪条绑定、为何是假命中（如"G 子串过宽，判据要告警 X、实际命中的是字段标签"）。禁止的排除理由："该配置很常见/看着正常"（树的判据就是故障标准，本技能无权推翻树：树说这个配置模式是故障因，它就是）、"证据量比别的候选少"、"与已确认根因同源"。①②都答不出的，老实放疑似或 undetermined；finalize 对 verdict=excluded 无 reason 直接拒收。
- `matched` 是证据量，`ratio` 只用于溯源：告警、日志类判据的分母是全量行数，命中占比天然是千分位；170 条告警命中就是 170 条证据，不因分母大而变弱，1 条命中也是成立（判据没写数量要求时）。不得以"匹配率低、占比小、只命中一条"为由降档、排除或压低置信度（实测：弱模型拿 0.8% 当"不足以支撑高置信度"降档、拿"只搜到一条"把已成立节点丢进待确认，均被拦下）。`ratio` 的正当用途只有一个：同一分类列内部比主次。
- 推荐解决方案（可选）：产物 `tree/solutions.json` 存在时（`{node_id: {"zh": …, "en": …}}`），给 `rca_result` 和 `probable_causes` 的每个条目按其根因节点的 `node_id` 点查，查到就在条目里加 `"recommend_solution"`（优先 zh，没有用 en），文字汇报也带上。只在定完根因后点查报出的那几个节点（不把整个文件读进上下文）；查不到就不加这个字段，不自己编方案；`undetermined` 不加（没定根因谈不上方案）。

## 8. 一句话

事实是别人查好的；本技能只做"拿故障树比对、如实判定"。候选自身成立、有判定的上级没有"不成立/冲突"才确证（未绑定或数据不足的上级默认放行并记入 caveat，报告提示"此处无判断"）；候选成立但上级实测不成立或冲突是层级矛盾，机械降为"疑似"（`blocked_at` 指认该上级）；候选自身不成立就排除；候选自身冲突要权衡；其余是数据不足。不用旁证硬顶、不造节点凑路径、不无中生有。
