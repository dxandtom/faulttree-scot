# 根因分析规则(fault-tree-rca,**指标无关**)

本技能只做一件事:**拿故障树 + 已解析好的各路事实,判定根因**。
它**不关心**指标具体是什么(今天是这几个,明天可以是任意新指标),下面的法则对**所有指标一视同仁**。

## 输入
- **fault_tree_md**:故障子树(`#/##/###` 层级,标题下是该节点的判断条件;人工编写、可能不规整)。
- **indicator_results**:dict,键是指标名,值是该指标已解析好的**事实**(只有数据、没有判断):每个字段/项的真实分布、数值摘要或取值。
  - 注意:有的指标提供的是**定义/规则**(某量怎么算、阈值是多少),而**不是实测值**。**定义不是测量。**
- 多数情况下每个指标的结果是**逐条件事实**:`{indicator,source,summary,conditions:[{id,node,condition_text,class,mapping_reason,fact}]}`,
  `fact.predicate_satisfied` 是**仅在解析到的列上做的字面比较**、`fact.status` 可能是 `insufficient_data`/`manual`。
  - 这是**输入证据,不是最终结论**:你仍要 ① 看 `mapping_reason` 判**语义是否真等**(如 RSRP 顶 RSSI、单位不符 → 降置信/数据不足,别因 `predicate_satisfied:true` 就当成立);② `status:insufficient_data/manual` → 该节点判"数据不足";③ **跨源组合**(同一判据的合取项分散在不同指标结果里)由你 AND/OR 合;④ 路径回溯与数据不足传播。**字面为真 ≠ 该条件成立。**
- 上下文可能已被**压缩成局部子树**:`fault_tree` 含 `outline`(`id→粗状态` 紧凑导航,**很小**)+ `pruned_nodes`(相关节点:`name/parent/level`、事实挂在 `facts` 里,另有 `condition`/`combine`/`pass_through`、**`is_leaf`(是不是叶子)/`uncovered_children`(下面带条件却没人绑的子因)**)+ `tree_issues` + `unmapped_facts` + **`uncovered_values`(判别列里出现却没被任何绑定认领的取值+条数 —— 据此把漏绑的记录归到保留的兜底节点,见下"覆盖度兜底")**。没有 index 时退回 `fault_tree_md`。**两种形态法则一样。**
  - **⚠ 输入可能很大:别一次性把整个 rca_input 读进上下文(会超长报错)。** **候选枚举交给代码**:先跑 `scripts/draft_rca.py <rca_input.json>` 生成骨架 `rca_draft.json`(成立节点→候选,路径/证据/how 已预填;draft_tier 是机械建议,你负责语义复核与定档,降档/不采纳都要落字,候选不许无声消失)。裁决中要看细节再用 `scripts/rca_query.py` 抽查(`--node nX` / `--outline` / `--holding`)。**别自己写脚本硬算**。
  - `outline` 的粗状态(`成立/不成立/数据不足/未覆盖/免检`,定义见输入自带的 `outline_legend`)只是**粗导航**——仍要按 `pruned_nodes` 的条件+事实**重判**,不许拿粗状态直接当判决书抄。**「成立」=有正向证据,这类节点不许丢待确认;「免检」=高层分类节点不参与判断,不是"检查通过"。**
  - node_id 是短 id(`nN`);`pass_through:true` 节点(汇总/"测试")**永不阻断路径**;`combine` 是 `AND/OR/unknown` 提示。
  - **node_id 权威**:`Fault_tree_path` 只用 `pruned_nodes` 里真实节点;`tree_issues.orphan_node_ids`/`unmapped_facts` 是绑定填错的信号,别据此硬判。
- **`knowledge`(可选)**:业务同事手写的**外挂知识**条目(`[{title, 适用?, text}]`,已按当前分支筛过)。
  它是**判读口径,不是事实**——两条用法红线:
  ① **可信其"怎么查/怎么解读/什么算正常"**:知识说"某现象属正常"(如双活网关一台 ping 不通)→ 对应
  候选按知识口径处理并在 caveats/排除理由里**引用知识标题**留痕;知识讲了查询方法/主次口径 → 照它解读事实;
  ② **不许拿知识顶替实测**:知识描述的现象/数值不能当 `actual` 引用,"知识说会这样"≠"数据里查到了"——
  成立仍要事实,缺数仍是数据不足。知识与事实**冲突**时以事实为准,并在 caveats 写明冲突。

## 核心:一个通用判定法则(不分指标)
对故障树**每条判断条件**,照此走:
1. 看清这条条件要的是**哪个量/字段/取值**(记作 **X**)。
2. 到 `indicator_results` 找 X 的**实际值**:
   - **找到 X 的实测值** → 代入条件的阈值/比较/算术 → 判"**成立 / 不成立**"。
   - **没找到**(没有这个字段;或某指标只给了 X 的**定义/规则**而非实测值;或 X 要的数据这次没提供)→ 判"**数据不足**"。
3. **绝不拿别的量 Y 顶替 X**:条件要 X、你手上只有相关的 Y,**不许用 Y 算个数就声称 X 成立**。"有定义"≠"有测量","有旁证"≠"该条件成立"。
4. **精确**:条件点名的取值/标识要**精确**命中(差一个字符就是没命中 → 数据不足),不许用相近值顶。

## 字段映射(树的量 ↔ 数据列):显式、按语义、可审、不许编
真实数据里**名字对不上是常态**:树的条件常用英文/code 名(如 `SUSRLastAvgRsrp`、`SA_QosFlow_Setup_Success_Rate`),
数据列却是中文(如 `上行RSSI均值`、`SA_QoSFlow建立成功率(22B)`)。所以第 1 步"找 X 的实际值"必须先**显式建立映射**,且:
1. **按含义映射,不按字符串**:在数据列里找"语义上就是这个量"的列。把这次映射**写进 evidence**(`mapping` + `mapping_reason`),让人能复核。
2. **找不到就数据不足,绝不抓个相关列顶替**:没有"就是 X"的列(如树要 SINR、数据里根本没有 SINR 列)→ 数据不足。
   **最隐蔽的错就是把 SINR 映到"语音用户数"这种只是恰好挨着/相关的列**——映射一旦错,后面数照样算得出、结论却全错且不报错。宁可数据不足,不可硬认。
3. **语义/单位近似要标注、降置信**:只有"相近但不等"的列(树要 RSRP、数据只有 RSSI;或量纲/口径不同,如本应 dBm 的列取值是 0.01/154 这种),
   可暂用但必须在 `mapping_reason` 写明差异,judgment 写"**语义近似/存疑**"(低置信),**不要**当干净的"成立/不成立";**有实测数据的节点别写"数据不足"**——数据是有的,那是对存在性撒谎,校验会点名(真缺数据才叫数据不足)。
4. **成功率 vs 原始计数**:树要 `尝试-成功`(差值)而数据只有百分比成功率、没有原始计数 → 要么数据不足,
   要么用"成功率<100%"重述同一问题**并在 `mapping_reason` 写明这是替代口径**,不得假装算出了差值。
5. **NIL / 空 = 缺测 = 数据不足**(对该单元格/该行),**绝不当"条件不成立"**——否则把"没测到"悄悄变成了"正常"。
   (解析事实里每列带 `nulls` 计数,缺测是显式可见的,别忽略。)
6. **阈值出处**:按故障树写的阈值用(那是现有权威);若树未标注出处,在 judgment 注明"阈值取自故障树、出处未核",不要当已验证门限。
7. **数值阈值条件怎么判**:数值列事实给了 `min/max/mean` 和**十分位 `deciles`**。
   "X < 阈值" 这类:用 deciles 估"有多少落在阈值一侧"(如阈值低于 `p0` → 基本无一命中;介于 `p20~p30` → 约两三成命中),
   并在 `actual` 写明你引用了哪些分位数;**够不够判一条成立由你按比例决定,但所引用的数必须逐字来自事实**。
   事实可带 **`hits`(命中原文片段,代码在命中位置截的窗)**——要在 `actual`/报告里展示"数据里那一行
   长什么样"时,**只许逐字抄 `hits`(或已含它的 `explain`)**,不许自己从数据里回忆/拼装原文。

8. **看分量,别只看"在场"**:C/G 字段匹配的事实现在带 `total`(纳入的非空行数)/`ratio`(matched/total)/`top`(同列取值分布)。`matched=87` 必须结合 `ratio`(占多少)和 `top`(其它错误码各多少)判**主次**——`87/90` 是主因、`87/50000` 多半是噪声;**排序、置信据此定,别拿裸 `matched` 当强证据**。**反过来,某取值占比畸高(≥90%、近乎恒在,正常样本里也是它)同样坐实不了特定子因——它不区分故障与正常,顶多当背景、绝不据此判 confirmed。**

## 路径分档:confirmed / probable / undetermined / excluded
一条候选 = 从某叶子回溯到根的路径。**铁律:不管判到哪一档,都要把理由说清。** 各档严格度不同:
- **confirmed(确证)——严**:终点必须是叶子(`is_leaf`),且根→叶路径上每个带条件节点都**干净成立**(无数据不足/不成立)。**成立的中间节点 ≠ 根因**(无 `is_leaf`/带 `uncovered_children` → 最多 probable,写"已定位到该层、叶子因待定")。**必须摆出完整 `evidence_path`**(每节点:条件/实际值/判断)。
- **probable(疑似)——松,交给你判**:路径里有"数据不足"**甚至"不成立"**节点都**允许**,只要叶子/关键节点有**正向证据**、你认为仍值得怀疑(那个"不成立"可能只是数据缺口/绑定假象)——这正是体现你泛化的地方。**但必须说清为什么只是疑似**:`blocked_at`(卡在哪个节点)+ `caveats`(上游为何不确定)+ `support`(支撑它的正向证据 + 有效样本量)。**理由不清 = 不合格。**
- **excluded(排除)**:你**有把握**这条路确实不通(可靠的"不成立"、无反证)→ 一句话带过,不进列表。**但排除的分支里若有节点带"成立"事实(如背景值/泛词命中),这"一句话"必须点名该节点留痕**(如顶层 `excluded_note`:"n136 BGP LSP震荡:子串命中系背景值,已排除")——校验器的候选对账靠这句认账,静默略过会被点名"漏裁决"。
- **undetermined**:既无正向证据、又缺数据。**有正向证据(哪怕只定位到中间层,如某计数器 87 条命中)就该进 probable,别丢这里。**
  **有 `ok+成立` 事实(outline 粗状态「成立」)的节点,不得作为待确认的阻塞点/理由/观察**——它有正向证据,按定义就不属于这档:升 probable(或有反证/系背景噪声则走排除并在 `excluded_note` 点名)。
  **"具体证据待查"不是合法理由**:证据已经在输入里,`rca_query --node nX` 拉出来判就是了——"待查"="我没查",属于工作没做完,不是档位依据(validate 会逐条点名)。
  **哪怕只命中 1 条也是成立**:判据原文没写数量要求的,1 条命中=条件成立(存在性语义,内核就按这判的);"只搜到一条、大部分行都不是"不构成待确认/降档理由——日志里故障行本来就是少数。
- **诚实底线(任何档都守,机器会查)**:`成立` 判断**必须对应一条真实的成立事实**;**绝不给"未覆盖/无 `facts`"的节点编一个"成立"**(局部子树已用 `is_leaf`/`uncovered_children`/有没有 `facts` 标出谁没数据)。**撒谎 ≠ 泛化。**

**只有这几条状态线是硬的(confirmed 必须全成立;有不成立就 excluded);其余全靠你判断:**
- **哪些够格的路值得报"疑似"、信心多高(high/medium/low)、怎么排序、写什么 caveat —— 你说了算**(用你的泛化能力)。机器不卡强度。
- **逐叶穷举、别过度合并(要报全)**:数据里每个有正向事实(matched>0 / 命中)的**不同**叶子或失败模式,都**各自**报一条(confirmed/probable;实在闭合不了至少进 `undetermined.observed` 逐条列),**别把几个不同叶子并成一条、也别只挑最强的一两条**——聚合数据常多种失败模式并存,尽量覆盖全。每条仍各自给真实事实 + caveat,**宁可多列几条带 caveat 的疑似,绝不为凑数编节点/编成立**。
- **别让"没绑上"的记录漏诊(覆盖度兜底)**:输入的 `fault_tree.uncovered_values` 列出了某**判别列**里出现过、却没被任何绑定认领的取值(+记录数)——这通常是生成侧漏绑了某一支。**即便绑定漏了,你也要据这些原始取值把记录归位**:剪枝**保留了**该支的"非典型场景/其他"兜底节点(在 `pruned_nodes` 里),按那个真实节点报一条(闭合不了就 probable / `undetermined.observed`),`actual` 附上原始特征码(如该 DCInnerCause 值 + 条数)。这正是"绑定错了、RCA 仍据事实救回来"的地方——别因为没人绑就当这些记录不存在。
- **疑似必须诚实披露**:卡在哪个节点(数据不足)、叶子证据是什么 + **有效样本量/空值比例**(如"96% 满足,但仅 1814/20496 非空")、为什么仍只是"疑似"。
- **绝不为了凑 confirmed 编节点/改路径**:路径只能用真实存在的节点;有数据不足节点就老实放 probable,**别造"测试""xx排查"之类不存在的节点把路凑完整**。
- **疑似 ≠ 确证**:别把疑似说成"已定位根因";它是"证据强、但路径未闭合(上游缺数据)"。

> 自检 `validate_rca.py <rca.json> <rca_input.json>` 只兜底线:对 **confirmed 严**(路径含数据不足/不成立、或缺 `evidence_path` → 揪),对 **probable 松**(只查理由齐不齐:`blocked_at`/`caveats`/`support`),**任何档**给"无事实"节点判"成立" → 揪(伪造)。**报错就挪档/补理由,别凑路径、别造节点、别给没数据的节点判成立。**

## tree_issues(顺带把子树的毛病报出来)
输入带 `tree_issues` 时,在输出 `tree_issues` 字段**原样带出、可补充**:`uncovered_condition_nodes`(有条件却没人绑/无数据源的节点)、`orphan_node_ids`(绑定填了不存在的节点)。这是给人改故障树/补数据的线索,**不影响根因判定**。

## 同节点多源事实的合成
多源同绑同一节点是期望行为(防漏),合成看**要件覆盖**(语义判断,你的活):
- 判据的**全部要件**都被 `ok+成立` 的事实覆盖(单源 D 组合覆盖全条,或多源各证各的要件)→ 节点**成立**;
- 其它源的"答不了/没查到"(insufficient)**不构成阻塞**——那是没来作证,不是反证,**别据此降档**;
- 要件有一块没被任何 ok 事实覆盖 → **只有那一块**算数据不足(对照判据原文数要件,别看"有没有 insufficient 事实");
- `成立` 与 `不成立` 并存,先看不成立那条是什么类:**存在类(C/G 非 absent)的未命中 = 弱阴性**——只说明"那份数据里没看见",**不构成反证**(告警表命中 2 条、日志表 0 命中 → 告警存在,成立;caveat 提一笔即可);**A 阈值/P 成对/absent 缺失类的不成立才是强反证** = 真冲突,权衡后写 caveat。draft 骨架已按此分拣(弱阴性带 `other_source_note` 留在候选,强反证进冲突区)。
(压缩形态下,剪枝已把"已确立节点"的 insufficient 事实剔掉;md 完整形态自己按本条合成。)

## 输出契约
```json
{
  "rca_result": [ {"Root_cause":"…","Fault_tree_path":["…"],"support":"…",
     "evidence_path":[{"node":"…","node_id":"…","condition":"<逐字取自故障树>",
        "mapping":"<树的量 X → 命中的数据列;没有写'无对应列'>","mapping_reason":"<为何这么对/差异/为何数据不足>",
        "actual":"<逐字引用事实(可引 deciles/nulls);没有写'事实中无此值'>",
        "how":"<怎么判的,一句人话——事实里带 explain 就逐字抄它(数字与规则不许改写),没有才按事实字段自己拼:在哪个数据的哪列找什么/算什么、实际得到多少、按什么规则判的>",
        "judgment":"成立/不成立/数据不足"}]} ],
  "probable_causes": [ {"Root_cause":"…","Fault_tree_path":["…"],"confidence":"high/medium/low",
     "blocked_at":"<路径上数据不足的节点>","caveats":"<有效样本量/空值比例/语义近似等>",
     "support":"<叶子证据>","evidence_path":[ …同上结构… ]} ],
  "undetermined": [ {"Fault_tree_path":["…"],"blocked_at":"…","reason":"缺哪个量","observed":["…(仅观察,非根因)"]} ],
  "tree_issues": { "uncovered_condition_nodes":[…], "orphan_node_ids":[…] }
}
```
- 每条 evidence 把 **条件 + 实际值 + 怎么判的(how)+ 判断** 写全;`pass_through` 中间节点注明"无独立条件"。
- **`how` 是给不懂技术、不懂判据分类的人看的**(报告和 HTML 直接展示它):事实里的 `explain` 字段就是机械拼好的这句话,**逐字抄、别改写数字**;它说清"在哪找什么→实际多少→按什么规则→结论",人对着它就能自行核验判断对不对。
- **给人看的字段用名字、别用 id**:`Root_cause`/`support`/`caveats`/`blocked_at`/`reason`/`observed` 一律写节点**名字**(必要时"名字(nN)"),**绝不只写裸 `nXX`**——人读报告不该还得去翻 tree 文件查 id 对应哪个节点。只有 `evidence_path` 里 `node_id` 填 nN(同条目 `node` 填名字),各司其职。
- **口径一致**:文字总结必须和 JSON 一致——`rca_result` 是 `[]` 就别说"发现了 N 条根因";疑似就叫疑似。
- `rca_result` 为 `[]` **很正常**(上游话统/信令缺数据时);**强证据放 `probable_causes`,别硬塞 `rca_result`、更别造节点凑路径**。
- **疑似档纪律**:每条疑似的 `evidence_path` 应包含**实际阻塞点**(有真判据且缺数据的节点)——路径全干净的该升确证;别把确证藏进疑似避审,也别拿疑似档当候选对账的泄压阀(validate 会逐条点名)。**全成立却居疑似 = 口径不符(validate 硬拦)**:凭主观怀疑降档可以,但怀疑必须落字到具体节点(该节点 judgment 写"语义近似/存疑"(有数据)或"数据不足"(真缺数)、blocked_at 写实);"单源/保险起见"不是降档理由。条目按 confidence 从高到低排;**文字汇报**详述 high/medium 的前几条,low 的合并成一行一条的简表——JSON 一条不少,治的只是噪音墙。
- **排除纪律(excluded_note)**:排除一个"判据成立"的候选,合法依据只有两种——①**反证**:该节点有 `ok+不成立` 的事实;②**绑定质量问题**:点名具体是哪条绑定、为何是假命中(如"G 子串过宽,判据要告警X、实际命中的是字段标签")。**禁止**的排除理由:"该配置很常见/看着正常"(**树的判据就是故障标准,你无权推翻树**——树说这个配置模式是故障因,它就是)、"证据量比别的候选少"、"与已确认根因同源"。①②都答不出的,老实放疑似或 undetermined——validate 会把每一次"排除成立且无反证的候选"晾出来核对。
- **matched 是证据量,ratio 只是溯源**:告警/日志类判据的分母是全量行数,命中占比天然千分位——170 条告警命中就是 170 条证据,**不因分母大而变弱,1 条命中也是成立**(判据没写数量要求时)。**不得以"匹配率低/占比小/只命中一条"为由降档、排除或压置信度**(实测:弱模型拿 0.8% 当"不足以支撑高置信度"赖档、拿"只搜到一条"把已成立节点丢待确认,均被拦)。ratio 的正当用途只有一个:同一分类列内部比主次。
- **推荐解决方案(可选,别光报病不给药)**:产物 `tree/solutions.json` 存在时(`{node_id: {"zh": …, "en": …}}`),给 `rca_result`/`probable_causes` 的每个条目按其**根因节点的 node_id** 点查,查到就在条目里加 `"recommend_solution"`(优先 zh,没有用 en),文字汇报也带上。**只在定完根因后点查报出的那几个节点**(别整个文件灌上下文);查不到就不加这个字段,**绝不自己编方案**;`undetermined` 不加(没定根因谈不上方案)。

## 一句话
事实是别人查好的;你只做"拿故障树比对、如实判定"。**全成立才算确证根因;有不成立就排除;强证据但上游缺数据 → 老实归"疑似"(带 caveat);其余数据不足。绝不用旁证硬顶、绝不造节点凑路径、绝不无中生有。**
