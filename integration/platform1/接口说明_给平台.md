# 故障树技能优化接口——调用说明(给平台侧)

## 一句话说清

你们在界面点「优化」→ 调我们这个接口,把导出的表和上一版 skill 的地址传过来 → 我们**立刻回"已受理"**
→ 后台迁移(几分钟到二十分钟)→ 做完由我们**调你们的回调接口**把新版 skill 文件传回去 → 你们置 COMPLETED。
调用是异步的:接口返回不代表做完,做完的信号是回调。

## 接口

- 地址:`POST http://<我方IP>:8080/optimize`
- 格式:`multipart/form-data`
- 字段:

| 字段 | 必填 | 说明 |
|---|---|---|
| `versionId` | 是 | 你们预生成的版本 UUID,**状态须为"优化中"**;回调时原样带回,你们按它匹配版本 |
| `excelFile` | 是 | 文件流。**全量表**(格式见下) |
| `prevObjectkey` | 是 | 上一版 skill 的 objectKey(与下载服务同一套地址)。**首次优化(无上一版)暂不支持**,会被拒且不回调——联调阶段请用已有 skill 的场景 |
| `optimizeType` | 是 | 请固定传 `ALL`(全量表、结构以表为准)。另有 `NONE`(问题不在节点,只刷引擎)/ `MULTI`(部分表,不动结构),一般用不上 |

- 响应:立刻 `{"result":"success"}`。只表示受理成功;要别的响应格式一句话我们改。
- 连通性自检:浏览器/curl 打 `http://<我方IP>:8080/docs` 能开就是通的。

curl 示例:
```
curl -X POST "http://<我方IP>:8080/optimize" \
  -F "versionId=<UUID>" -F "optimizeType=ALL" \
  -F "prevObjectkey=skill-wheel/fault-tree/node/xxxx.zip" \
  -F "excelFile=@全量表.xlsx"
```

## 表怎么给(全量表)

树上**每个节点一行**(含根和中间层),列名:

`L1_Name_CN | L1_Name_EN | … | Ln_Name_CN | Ln_Name_EN | judgement_condition_cn | judgement_condition_en | solution_cn | solution_en | Product_Obs | Product_Name | 是否修改`

三条硬规矩:
1. **每个节点自己的包、自己的 objectKey**。同一个 objectKey 挂到多个节点名下会被当成导表错位,直接拒(不下载不迁移)。
2. **已有节点的判据列(judgement_condition_cn)必须带上现有判据**。判据空 + 包也空 = "清除该节点的判据和绑定",不是"没改"。
3. 改了的行 `是否修改` 填 `是`(或 Y/1)。只有标记行会做迁移/判据同步/方案同步;未标记行的包不下载。

结构语义:表里没出现的节点 = 删除(有防误删保险,删太多会整体拒);树上没有的新行 = 新增(有包就绑脚本,只有判据就建结构节点)。解决方案列可选,空不代表删除。

## 做完怎么知道

我们回调:`POST https://<网关主机>/agent/workspace/faultTreeNode/optimizeCallback`,`multipart`:`versionId` + `skillFile`(新版 skill 的 zip 文件流),请求头带 `invokeToken`(与下载服务同一套鉴权)。你们收到后上传 OBS、置 COMPLETED。

耗时参考:节点脚本没问题 1~2 分钟;脚本要修(常见:数据文件只认 .txt、缺数据判成 false)10~20 分钟。

## 哪些情况不会回调(版本会停在"优化中")

1. 首次优化(prevObjectkey 为空);
2. 表错位或包下载失败(objectKey 对不上、对象已不存在);
3. 一行都没落地(回传一个没变化的包只会误导版本记录)。

这三种目前只能由我们看日志定位,请把 **versionId** 发给我们。"失败/部分成功"回调字段你们定下来后,这些情况会改为回调告知。

**部分成功照常回调**:已落地的节点先生效,成功/跳过/失败清单连原因在包内 `tree/migration_report.json`。

## 一次点击 = 一轮

每次点优化只做一轮处置就交付;没修完的节点,下次点优化会在新版 skill 的基础上继续。内容没变的节点自动跳过,反复点不会重复改。
